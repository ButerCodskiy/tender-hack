## 1. Структура каталога Markdown: Документно-ориентированная

### Решение:
Генерация единого Markdown-файла на каждый документ: `markdown/{doc_slug}.md` + корневой `markdown/README.md` со сводным каталогом базы знаний.

### Детали реализации:
1. **Транслитерация и Slug-генерация:**
   - Для имен файлов используется стандартная транслитерация кириллицы в латиницу (без сторонних зависимостей) с очисткой спецсимволов:
     `"Положение о закупках 44-ФЗ" -> "polozhenie_o_zakupkakh_44_fz"`.
   - Защита от коллизий: при совпадении slug добавляется суффикс `_2`, `_3`.
2. **Структура `markdown/README.md` (Каталог для жюри):**
   - Заголовок и метаданные экспорта: дата генерации, режим парсинга, общее число документов.
   - Сводная таблица всех документов:
     * Название документа
     * Ссылка на файл `{doc_slug}.md`
     * Идентификатор `doc_id`
     * Число страниц
     * Число узлов AST
     * Число чанков
     * Полнота извлечения символов (Docling / PyMuPDF %)
     * Статус проверки
3. **Структура `{doc_slug}.md`:**
   - **Заголовок документа (`#`)** и блок метаданных (doc_id, режим, дата редакции, источник).
   - **Оглавление (TOC)** с якорными ссылками на заголовки разделов.
   - **Тело документа:**
     * Разделы, статьи и пункты с нативной иерархией заголовков (`##`, `###`, `####`), сформированной по узлам `kb_nodes`.
     * Таблицы в формате GitHub Flavored Markdown (`table_md`).
     * В конце каждого логического фрагмента или узла — якорная сноска или маркер чанка:
       `> 🔖 **Чанк:** \`chunk_id\` (токенов: N, таблица: да/нет)`
       Это обеспечивает прямую сквозную навигацию от текста к векторному хранилищу без спама в файловой системе.

## 2. Состав и упаковка архива `kb_export.zip`

### Решение:
Гибридный архив, включающий как машиночитаемые JSON-дампы, так и человекочитаемое дерево Markdown.

### Содержимое архива `kb_export.zip`:
```text
kb_export.zip
├── parsed_documents.json      # Таблица kb_documents (метаданные)
├── parsed_nodes.json          # Таблица kb_nodes (иерархическое дерево AST)
├── parsed_chunks.json         # Таблица kb_chunks (векторизуемые фрагменты)
├── completeness_reports.json  # Журнал контроля полноты PyMuPDF vs Docling
├── summary_statistics.json    # Сводные агрегированные метрики объемов
└── markdown/                  # Человекочитаемая витрина для жюри
    ├── README.md              # Индекс-каталог с гиперссылками
    ├── doc_44fz.md
    └── ...
```

### Безопасность и атомарность:
- Использование стандартного модуля `zipfile` с режимом сжатия `zipfile.ZIP_DEFLATED`.
- Упаковка через временный файл `.tmp` с атомарным переименованием (`os.replace`) во избежание повреждения архива при прерывании процесса (Ctrl+C).

## 3. Автоматический роутинг FAQ таблиц (`.xlsx`, `.csv`)

### Решение:
Автоматическое определение типа контента на входе `ingest --dir`:
- Файлы `.xlsx`, `.xlsm`, `.csv` валидируются на наличие структуры вопросов и ответов через эвристики `FaqParser._find_header_columns`.
- При успешном обнаружении колонок (Вопрос/Ответ) данные парсятся в `FaqRow` и трансформируются в унифицированные схемы:
  * `ParsedDocumentSchema` (синтетический документ FAQ)
  * `ParsedNodeSchema` (контейнерный узел)
  * `ParsedChunkSchema` (каждая пара вопрос-ответ становится чанком `chunk_faq_*` с `has_table=False`)
- Файлы регламентов (`.pdf`, `.docx`, `.txt`, `.md`) направляются в конвейер `DocumentParser` (Docling + PyMuPDF).
- Все документы, узлы и чанки объединяются в единые выходные массивы `parsed_documents.json`, `parsed_nodes.json`, `parsed_chunks.json`.

## 4. Отказоустойчивость батча и коды завершения

### Решение:
Стратегия **Best-effort**: единичный битый файл не должен обрывать часовой процесс обработки десятков регламентов.

### Логика обработки ошибок:
1. Ошибка разбора конкретного файла перехватывается, логируется со стек-трейсом через `logger.exception`.
2. Информация об ошибке фиксируется:
   - В списке `failed_files` в файле `summary_statistics.json` (имя файла, ошибка, тип ошибки).
   - Если был сформирован объект документа — статус переводится в `failed`.
3. Успешно распарсенные файлы сохраняются инкрементально на диск после каждого шага.
4. **Коды завершения процесса (CLI Exit Codes):**
   - `0` — Все файлы успешно обработаны без ошибок.
   - `2` — Частичный успех (Warning): часть файлов обработана успешно, но есть ошибки в 1 или нескольких файлах.
   - `1` — Критический инфраструктурный сбой (директория не существует, нет прав на запись и т.п.).

## 5. Сводная статистика и консольный отчет полноты

### Решение:
По окончании работы `ingest` в терминал и в файл `summary_statistics.json` выводятся две структурированные таблицы:

1. **Сводная статистика объемов базы знаний:**
   - Общее число обработанных документов (успешно / с ошибками).
   - Число страниц (суммарно по PDF/DOCX).
   - Число узлов AST (с разбивкой по уровням: `section`, `article`, `item`).
   - Число чанков (суммарно, средний размер в токенах, максимальный размер).
   - Число таблиц (извлечено сеток Markdown и линеаризованных фактов).
   - Общее время обработки и средняя скорость (страниц/сек, токенов/сек).

2. **Отчет контроля полноты извлечения символов (PyMuPDF Validation):**
   - Документ | Символов Docling | Символов PyMuPDF | Расхождение % | Графический скан | Ручная проверка
   - Четкая индикация документов, требующих внимания методистов (`needs_manual_review = True` при дельте > 5%).
