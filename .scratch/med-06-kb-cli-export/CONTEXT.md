## 1. Паспорт задачи

- **Идентификатор:** `MED-06`
- **Название:** Консольная команда пакетной загрузки и экспорт артефактов базы знаний
- **Исполнитель:** Разработчик 3 (База знаний, парсинг, конвейер Ingestion)
- **Целевая зона в кодовой базе:** `backend/src/kb/cli.py`
- **Блокирующие зависимости:** 
  - `HIGH-05` (Конвейер глубокого разбора документов регламентов и таблиц — реализован в `parser.py`, `chunker.py`, `tables.py`)
  - `HIGH-06` (Импорт структурированных таблиц типовых вопросов и ответов — реализован в `faq_loader.py`)

### Критерии приемки из роадмапа:
1. Создана консольная команда `ingest --dir <folder>` для пакетной обработки предоставленных организаторами методичек.
2. Формируется отчет о полноте извлечения символов с валидацией через PyMuPDF.
3. Реализован экспорт структурированной базы знаний в единый архив JSON и дерево файлов Markdown для демонстрации жюри.
4. Формируется сводная статистика по объему документов, узлов, фрагментов и таблиц.
5. **Ручная проверка:** запустить в терминале команду:
   ```bash
   uv run python -m src.kb.cli ingest --dir storage/kb_documents
   ```
   проконтролировать вывод статистики разбора документов и убедиться в создании выгрузки архива JSON и файлов Markdown для жюри.

## 2. Текущее состояние кодовой базы в целевой зоне

### Что уже есть:
- **`backend/src/kb/cli.py`** (266 строк):
  - Базовая реализация подкоманды `ingest` с аргументами `--input`/`-i`, `--out-dir`/`-o`, `--doc-id`, `--regime`, `--mode`, `--no-profile`.
  - Пакетный обход файлов (`.pdf`, `.docx`, `.txt`, `.md`) с прогресс-баром `tqdm`.
  - Атомарное сохранение артефактов через временные `.tmp` файлы (`atomic_write_json`):
    * `parsed_documents.json` (список документов)
    * `parsed_nodes.json` (список узлов AST)
    * `parsed_chunks.json` (список поисковых чанков)
    * `completeness_reports.json` (отчеты контроля полноты)
    * `profiling_report.json` (тайминги и метрики памяти)
  - Интеграция с `DocumentParser` (`src.kb.parser`) и `PipelineProfiler` (`src.kb.profiler`).
- **`backend/src/kb/parser.py`**:
  - Метод `DocumentParser.extract_pymupdf_text(file_path)`: извлечение символьного слоя через PyMuPDF (`fitz`), подсчет непробельных символов.
  - Метод `DocumentParser.validate_completeness(doc_id, pymupdf_char_count, docling_char_count)`: расчет `discrepancy_ratio`, детекция графических сканов (`is_scanned`) и флага ручной проверки (`needs_manual_review` при дельте > 5%).
- **`backend/src/kb/schemas.py`**:
  - `CompletenessReportSchema`, `ParsedDocumentSchema`, `ParsedNodeSchema`, `ParsedChunkSchema`, `ParsedExtractionResultSchema`.

### Чего нет / что не соответствует спецификации:
1. **Сигнатура аргументов CLI:**
   - Роадмап строго требует `ingest --dir <folder>`. В текущем `cli.py` обязательными являются `--input` и `--out-dir`. Запуск `python -m src.kb.cli ingest --dir storage/kb_documents` падает с ошибкой `unrecognized arguments: --dir`.
   - `--out-dir` не имеет значения по умолчанию (должен по умолчанию сохранять в `storage/kb_export` или `parsed_kb`).
2. **Экспорт дерева Markdown для жюри:**
   - Полностью отсутствует генерация дерева файлов Markdown (`.md`), отображающего иерархию регламентов, разделы, статьи, таблицы и метаданные фрагментов.
3. **Единый архив JSON:**
   - Отсутствует упаковка сгенерированных JSON-файлов и дерева Markdown в единый архив (`.zip`), готовый к передаче жюри или выгрузке.
4. **Сводная статистика и консольный отчет о полноте PyMuPDF:**
   - Отчеты о полноте пишутся только в `completeness_reports.json`, но в консоли не выводится сводная таблица контроля полноты (Docling chars vs PyMuPDF chars, процент извлечения, детекция сканов).
   - Нет сводной статистики по общему числу документов, узлов AST, чанков, таблиц и токенов (отдельный блок summary statistics).

## 4. Точки интеграции со смежными доменами

1. **Домен `kb` (`DocumentParser`, `HierarchicalChunker`):**
   - Прямой вызов `parser.parse_document()` возвращает типизированный `ParsedExtractionResultSchema`.
2. **Файловая система (`storage/kb_documents/`):**
   - Каталог регламентов по умолчанию согласно `settings.KB_STORAGE_DIR`.
3. **Презентационный контур для жюри:**
   - Дерево файлов Markdown должно быть структурировано так, чтобы любой член жюри или методист мог открыть директорию в VS Code / GitHub / Obsidian и прочитать статьи регламента в исходном виде с таблицами и сносками на чанки.
   - Единый архив `kb_export.zip` содержит и программные структуры (JSON), и человекочитаемые файлы (Markdown).

## 5. Архитектурные развилки и риски для сессии `/grill-me`

1. **Структура дерева Markdown:**
   - *Вариант А:* Плоская папка `markdown/` с файлами `doc_id.md` (или `Название_документа.md`), где внутри оформлены разделы, заголовки, таблицы и сноски на `chunk_id`.
   - *Вариант Б:* Иерархическое дерево папок по `section_path`: `markdown/{doc_title}/{section}/{article}.md`.
   - *Вопрос:* Какой формат наиболее презентабелен и удобен для жюри хакатона?
2. **Формат и состав единого архива JSON:**
   - Упаковывать ли в `kb_export.zip` только JSON-файлы (`parsed_documents.json`, `parsed_nodes.json`, `parsed_chunks.json`, `completeness_reports.json`, `summary_statistics.json`), либо включать туда же всё дерево файлов Markdown?
3. **Интеграция с FAQ (`HIGH-06`):**
   - Должна ли команда `ingest --dir` автоматически подхватывать и парсить таблицы вопросов-ответов (`.xlsx`, `.csv`) через `FaqLoader`, либо обрабатывать их параллельно с регламентами?
4. **Поведение при пустой папке или ошибках отдельных файлов:**
   - Должен ли CLI падать с ненулевым кодом возврата при ошибке одного документа из пакета, либо продолжать обработку остальных (Fault Tolerance) и формировать отчет об ошибках в `summary_statistics.json`?
5. **Производительность и режим по умолчанию:**
   - По умолчанию использовать `--mode fast` или `--mode accurate`? Fast быстрее на порядок для цифровых PDF методичек, но accurate запускает TableFormer.
