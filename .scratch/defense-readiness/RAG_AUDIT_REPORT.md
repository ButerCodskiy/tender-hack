## 2. Детальный разбор по пунктам аудита

### ПУНКТ 1. Механика отказа отвечать (Out-of-Domain & Low Confidence)

#### 1.1. Что реально происходит при вопросе не по теме («Как испечь торт?», «Напиши стих»)?
1. Входящий запрос из эндпоинта `POST /chat/messages` попадает в [`ChatService.process_client_message`](../../backend/src/chat/service.py#L154).
2. Запрос проверяется **только на ненормативную лексику** (мат) через `moderator.validate_client_message()`. Проверки на предметную область на входе нет.
3. Далее создается `active_ticket` с жестко зашитым `priority=P2` и сразу вызывается:
   ```python
   rag_request = RagQueryRequestSchema(query=payload.text, message_id=bot_message_id)
   async for event in self.rag_service.generate_answer(rag_request): ...
   ```
4. В [`RagService.generate_answer`](../../backend/src/rag/service.py#L48):
   - Эмитируются фейковые события со `sleep(0.01)`: `classifying` -> `searching` -> `reranking`. Реальная классификация **не вызывается**.
   - Вызывается `chunks = await self.retriever.retrieve(query)`.
5. В [`Retriever.retrieve`](../../backend/src/rag/retriever.py#L73):
   - Запрос векторизуется и отправляется в Qdrant:
     ```python
     response = await self.qdrant_client.query_points(
         collection_name=collection,
         query=dense,
         limit=self.top_k,
         with_payload=True,
     )
     ```
   - **Косинусный поиск Qdrant всегда возвращает ближайшие $K$ точек, даже если сходство минимально (например, score = 0.12).**
   - **ПРОВЕРКА ПОРОГА СКОРА (`score_threshold`) ОТСУТСТВУЕТ ПОЛНОСТЬЮ.** В коде `retriever.py` нет ни `score_threshold` в параметрах Qdrant, ни строки `if point.score < THRESHOLD: continue`.
6. Результат: список `chunks` **НЕ ПУСТОЙ**. В него попадают 5–10 случайных фрагментов регламентов закупок.
7. Проверка `if not chunks:` в [`service.py:83`](../../backend/src/rag/service.py#L83) **НЕ СРАБАТЫВАЕТ**.
8. Запрос `«Как испечь торт?»` вместе с фрагментами регламентов закупок падает в LLM!
9. Модель получает системный промпт с правилом `DEFLECTION RULE` («Если информации нет — скажи, что информации нет»). Однако компактная модель (в конфигурации `qwen3.5:2b-instruct`) при наличии контекста часто игнорирует негативные ограничения и начинает либо генерировать рецепт из своих предобученных весов, либо пытаться составить рецепт из слов регламента закупок.

#### 1.2. Что происходит, если Qdrant действительно вернул пустой список?
- Только в случае, если коллекция Qdrant физически пуста или сервис Qdrant упал с ошибкой и вернул `[]`:
  Срабатывает условие в [`service.py:83-92`](../../backend/src/rag/service.py#L83-L92):
  ```python
  if not chunks:
      yield RagDegradedModeEventSchema(
          message=(
              "Информация по вашему запросу не найдена в нормативных регламентах "
              "Портала поставщиков Москвы. Пожалуйста, уточните вопрос или "
              "обратитесь к специалисту поддержки."
          ),
          sources=[],
      )
      return
  ```
  В этом сценарии модель действительно не вызывается. Но на практике при заполненном индексе Qdrant **никогда не возвращает пустой список без явного score threshold**.

#### 1.3. Поведение на смолл-толки («Привет», «Спасибо», «Как дела»)
- **Выкидывает ли их на поддержку?** НЕТ.
- Они проходят полный цикл: векторизация -> поиск в Qdrant случайных чанков -> отправка в LLM.
- Модель получает чанки про котировочные сессии на слово «Привет» и либо генерирует формальный ответ со ссылкой на регламент, либо заявляет об отсутствии информации по «Привет».

#### 1.4. Поиск с контекстом и без / Rewrite запроса
- В `ChatService` строка [`chat/service.py:191`](../../backend/src/chat/service.py#L191):
  Поле `conversation_history` **не передается вовсе** (всегда `None`).
- Никакого параллельного поиска (с контекстом / без контекста) в `Retriever` нет.
- Никакого переформулирования запроса (Query Rewrite в `standalone_query`) перед поиском в Qdrant нет.

### ПУНКТ 2. Сборка контекста (Context Assembly)

#### 2.1. Какой текст реально передается в системный и пользовательский промпт LLM?
Формирование выполняется в [`format_rag_prompt`](../../backend/src/rag/prompts.py#L36-L80):

1. **Системный промпт (`system_prompt`):**
   ```text
   Ты — интеллектуальный эксперт-консультант службы поддержки Портала поставщиков Москвы и регламентов государственных и коммерческих закупок (44-ФЗ, 223-ФЗ).
   Твоя цель — предоставить точный, юридически и технически выверенный ответ на вопрос пользователя строго на основе переданных нормативных документов.
   КРИТИЧЕСКИЕ ПРАВИЛА:
   1. ИСТОЧНИКИ И СНОСКИ: Отвечай исключительно на основе предоставленных нормативных источников ([Источник N | ...]). Подтверждай каждое требование сноской [^N]...
   2. СТРОГИЙ ЗАПРЕТ ВЫМЫСЛА (DEFLECTION RULE): Если в предоставленных фрагментах НЕТ информации... прямо заяви: «В предоставленных регламентах и нормативных документах информация по вашему вопросу отсутствует. Рекомендуем обратиться к оператору...»
   3. СТИЛЬ И ФОРМАТИРОВАНИЕ: Деловой точный тон, списки Markdown...
   ```

2. **Пользовательский промпт (`user_prompt`):**
   ```text
   Найденные нормативные регламенты и статьи:

   [Источник 1 | Регламент котировочных сессий > Раздел 4 | Раздел 4. Подписание протоколов]
   {quote_text}

   [Источник 2 | Инструкция по работе с ЕРУЗ | Регистрация]
   {quote_text}

   ---

   Вопрос пользователя:
   {query}
   ```
   *(Блок «История предыдущего диалога» опускается, так как `conversation_history` не передан из `chat/service.py`).*

#### 2.2. Реализована ли связка Small-to-Big (подтягивание `kb_nodes.content_markdown`)?
В коде [`retriever.py:119-178`](../../backend/src/rag/retriever.py#L119-L178) логика гидратации **написана**:
1. Из найденных точек Qdrant извлекаются `node_id`.
2. Выполняется запрос к PostgreSQL:
   ```sql
   SELECT id, content_markdown, section_path, title, doc_id 
   FROM kb_nodes WHERE id = ANY(:node_ids)
   ```
3. Если строка найдена в `kb_nodes`:
   `quote_text = parent_node.content_markdown`
4. Если не найдена:
   `quote_text = point.payload.get("text")` (сырой чанк из Qdrant).

**Критические проблемы связки Small-to-Big в текущем коде:**
1. **Отсутствует лимит токенов родительского узла:** Спецификация (§16) требовала ограничение `token_count <= 2500`. В `retriever.py` никакого усечения нет. Если родительский раздел в Markdown занимает 15 000 символов, он целиком попадает в `quote_text`. Два таких раздела переполнят контекстное окно Ollama/Qwen.
2. **Тихий откат на сырой чанк:** Если миграция PostgreSQL не применена или база пуста, блок `try/except` в строке 140 тихо ловит ошибку и оставляет сырой `text` из Qdrant.

#### 2.3. Форматирование метаданных
Метаданные форматируются функцией [`format_context_chunk`](../../backend/src/rag/prompts.py#L27-L33):
`[Источник {idx} | {section_path} | {title}]\n{body}`
- `section_path`: хлебные крошки AST (например: `Инструкция поставщика > Раздел 3 > Пункт 3.2`). Если поле пустое, подставляется fallback `"Общий раздел"`.
- `title`: заголовок статьи/раздела. Если пусто, подставляется `"Документ {doc_id}"`.

### ПУНКТ 3. Валидация ответа и защита от галлюцинаций (FactChecking / Guardrails)

#### 3.1. Существует ли `FactCheckingGuard` в кодовой базе?
**ДА, СУЩЕСТВУЕТ В КОДЕ.**
- **Файл:** [`backend/src/rag/generator.py`](file:///c:/Users/Дмитрий/Desktop/git/tender-hack/backend/src/rag/generator.py#L135-L203).
- **Класс:** `FactCheckingGuard`.
- **Ключевые методы:**
  - `extract_footnotes(text)` (строка 140) — парсит индексы сносок `[^1]`, `[1]`.
  - `extract_numeric_facts(text)` (строка 144) — вырезает сами сноски, нормализует пробелы в числах (`500 000` -> `500000`), слеши в датах (`15/10/2024` -> `15.10.2024`) и собирает множество числовых фактов.
  - `verify_sentence(sentence, chunks, allowed_query_numbers)` (строка 160) — выполняет сопоставление чисел предложения с числами из чанков, указанных в сносках.
- **Покрытие тестами:** [`backend/tests/rag/test_generator.py`](file:///c:/Users/Дмитрий/Desktop/git/tender-hack/backend/tests/rag/test_generator.py#L101-L200). Все 8 юнит-тестов валидатора зеленые.

#### 3.2. Почему это НЕ защищает от галлюцинаций в текущем виде?
В методе генерации [`RagStreamGenerator.generate_response_stream`](../../backend/src/rag/generator.py#L257-L288):
```python
async for token in stream:
    completed = buffer.feed(token)
    for sentence in completed:
        verified = self.guard.verify_sentence(
            sentence, chunks, query_numbers
        )
        if not verified:
            all_verified = False
        full_text_parts.append(sentence)
        yield RagSentenceEventSchema(
            sentence_idx=sentence_idx,
            text=sentence,
            verified=verified,
        )
        sentence_idx += 1
```

**Критический архитектурный изъян:**
1. Если модель выдумала срок или сумму, `FactCheckingGuard` честно возвращает `verified = False`.
2. Но генератор **НЕ ОБРЫВАЕТ стриминг, НЕ МАСКИРУЕТ предложение и НЕ ЗАМЕНЯЕТ его на предупреждение**.
3. Предложение с галлюцинацией **напрямую отправляется клиенту в SSE-событии `sentence`**.
4. Фронтенд (`frontend/src/services/api.ts:218-223`) просто конкатенирует `sentence` в общий текст сообщения. Пользователь видит недостоверную цифру на экране!
5. То есть `FactCheckingGuard` сейчас работает как **пассивный телеметрический аудитор**, а не как **активный защитный барьер (Guardrail / Circuit Breaker)**.

### ПУНКТ 4. Сноски и цитирование

#### 4.1. Формирует ли промпт сноски вида `[^1]`, `[^2]`?
- **ДА.** Системный промпт ([`prompts.py:11-14`](../../backend/src/rag/prompts.py#L11-L14)) строго требует:
  `«Подтверждай каждое нормативное требование, порядок действий, срок, процент или сумму сноской вида [^N], где N — порядковый номер источника из переданного списка (например: [^1], [^2]). Запрещено указывать сноски на номера источников, которые отсутствуют в переданном списке.»`
- В `SentenceBuffer` используется `razdel.sentenize`, который корректно сохраняет маркер `[^1]` в конце предложения.
- В `FactCheckingGuard` индекс сноски исключается из числовых фактов регуляторным выражением `FOOTNOTE_REGEX.sub("", text)`, что предотвращает ложные срабатывания валидатора на сам номер сноски.

#### 4.2. Передаются ли метаданные сносок в API и на фронтенд?
- **ДА.** В начале ответа [`RagService.generate_answer`](../../backend/src/rag/service.py#L94) отправляет SSE-событие:
  `event: sources` с полным массивом `sources: list[RagSourceChunkSchema]`.
- Каждая запись содержит:
  - `chunk_id`
  - `doc_id`
  - `title` (название регламента / статьи)
  - `section_path` (иерархический путь по AST)
  - `quote_text` (текст цитаты)
  - `relevance_score`
- В [`ChatService.process_client_message`](../../backend/src/chat/service.py#L213-L227) эти источники сохраняются в БД в таблицу `message_sources`.
- Во фронтенде ([`frontend/src/services/api.ts:200-216`](../../backend/src/frontend/src/services/api.ts#L200-L216)) событие `sources` перехватывается, преобразуется в массив `citations` и передается в UI для кликабельного отображения шторки цитат.

## 3. Реестр критических дыр в RAG (Требуют закрытия до демо)

### Дыра 1. Отсутствие порога релевантности в ретривере (Low Confidence Leak)
- **Суть:** В [`retriever.py`](../../backend/src/rag/retriever.py#L83-L116) Qdrant возвращает кандидатов с любым скором. Запросы не по теме затягивают мусорные регламенты в LLM.
- **Риск на демо:** Жюри вводит вопрос «Сколько варить пельмени?» или «Кто президент Франции?» — бот выдает абсурдный ответ с цитатами из 44-ФЗ.
- **Решение:** Ввести проверку: если максимальный `score` среди найденных точек $< 0.45$ (или использовать `score_threshold=0.45` в Qdrant), ретривер возвращает пустой список `[]`. Тогда `RagService` детерминированно отдаст `RagDegradedModeEventSchema` с официальным отказом и кнопкой вызова оператора.

### Дыра 2. «Мертвый» QueryRouter (Полная изоляция от чата)
- **Суть:** В кодовой базе есть готовый, протестированный модуль [`router.py`](../../backend/src/rag/router.py) (544 строки) с определением тем, линий поддержки (L1/L2/L3), приоритетов (P0/P1/P2) и интентов (`chitchat`, `out_of_domain`). Но `ChatService` **НЕ ВЫЗЫВАЕТ ЕГО**. Все тикеты создаются с `priority=P2`, `line=None`.
- **Риск на демо:** При вводе ошибки `0x80090016` или угрозы судом тикет не эскалируется в L2/P0, а падает в общую очередь L1 со стандартным приоритетом.
- **Решение:** Подключить вызов `QueryRouter.route()` в `ChatService.process_client_message` перед обращением к RAG:
  1) При `intent == 'chitchat'` отдавать быстрый приветственный ответ без RAG и без создания сложного тикета.
  2) При `intent == 'out_of_domain'` отдавать вежливый отказ («Я консультирую только по вопросам Портала поставщиков и госзакупок»).
  3) Присваивать тикету реальные `line_id` и `priority`, определенные роутером.

### Дыра 3. FactCheckingGuard не блокирует галлюцинации (Пассивный наблюдатель)
- **Суть:** В [`generator.py:260-271`](../../backend/src/rag/generator.py#L260-L271) при `verified=False` предложение все равно отдается клиенту.
- **Риск на демо:** Если модель исказит сумму обеспечения (назовет 5% вместо 1%), клиент увидит ошибку в чате.
- **Решение:** Если предложение содержит числа и `verified == False`:
  Либо заменять текст предложения на предупреждение: `«[Внимание: данные о сроках/суммах требуют уточнения у оператора]»`, либо обрывать генерацию и переводить сессию в Soft Deflection.

### Дыра 4. Потеря истории диалога в RAG
- **Суть:** В [`chat/service.py:191`](../../backend/src/chat/service.py#L191) `RagQueryRequestSchema` создается без `conversation_history`.

### Дыра 5. Пустой `reranker.py` и фейковый статус `reranking`
- **Суть:** Файл [`reranker.py`](../../backend/src/rag/reranker.py) пуст. `service.py` шлет пользователю статус `«Анализ точности найденных статей...»`, имитируя работу реранкера через `sleep(0.01)`.
- **Риск на демо:** Вопрос жюри на защите: «Где у вас крутится Cross-Encoder reranker? Покажите код вызова TEI/bge-reranker-v2-m3». В коде будет обнаружен пустой файл.
- **Решение:** Либо убрать статус `reranking` из генератора, честно сказав, что ранжирование выполняет Qdrant, либо реализовать минимальный вызов локальной модели/клиента реранкера.

### Дыра 6. Конфликт конфигураций эмбеддингов
- **Суть:** В `.env` указано `EMBEDDING_MODEL_NAME=sentence-transformers/paraphrase-multilingual-MiniLM-L12-v2` и `ENABLE_LOCAL_NEURAL_EMBEDDINGS=False`. В `retriever.py` захардкожена `BAAI/bge-m3` с размерностью 1024. В `ingest_adr0001.py` размерность 1024.
- **Риск на демо:** При перезапуске бэкенда без CUDA/Transformers ретривер падает на fallback `EmbeddingStub`, который генерирует псевдохеши вместо эмбеддингов, полностью ломая семантический поиск в Qdrant.
- **Решение:** Явно синхронизировать `.env` и настройки `retriever.py`: зафиксировать единую размерность 1024D и модель `BAAI/bge-m3`.
