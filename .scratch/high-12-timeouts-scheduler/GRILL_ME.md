## 1. Защита от спама предупреждениями у оператора (10 vs 15 минут)

### Контекст проблемы:
Задача `check_system_timeouts` запускается планировщиком Taskiq Scheduler каждые 30 секунд. Между 10-й минутой (отправка напоминания «Вы еще здесь?») и 15-й минутой (принудительное закрытие `closed_by_inactivity`) проходит 5 минут, что соответствует **10 последовательным тактам выполнения планировщика**. Если клиент продолжает молчать, наивная проверка по `updated_at < now() - 10 min` приведет к тому, что клиент получит 10 дублирующихся системных сообщений подряд с интервалом в 30 секунд.

### Сравнительный анализ вариантов фиксации предупреждения:

1. **Флаг в таблице `tickets` (`inactivity_warning_sent: bool`):**
   - *Минусы:* Требует миграции схемы БД Alembic. Флаг узкоспециализирован и нарушает третью нормальную форму (состояние диалога размазывается между таблицами).
2. **Временный ключ в Redis с TTL (`ticket:warning_sent:{ticket_id}`, TTL 360 с):**
   - *Минусы:* Redis — не персистентный источник истины. При аварийном рестарте Redis или потере ключа клиент снова получит спам. Нарушается принцип единого источника правды (Single Source of Truth в PostgreSQL).
3. **Реляционная проверка по истории сообщений в таблице `messages` (Рекомендуемое решение):**
   - *Плюсы:* Полное отсутствие миграций БД, 100% персистентность и строгая идемпотентность.
   - *Механика:* 
     При анализе тикета в статусе `in_progress` проверяются параметры **последнего сообщения** (`messages` с максимальным `created_at` для данного `ticket_id`):
     - **Случай А (кандидат на предупреждение):**
       - Последнее сообщение отправлено оператором (`sender_type == 'operator'`).
       - Возраст последнего сообщения $\ge 10$ минут (`created_at <= now - 10 min`).
       - *Действие:* Сервис сохраняет в `messages` системную реплику (`sender_type = 'system'`, текст: `«Вы еще здесь?»`), обновляет `tickets.updated_at = now()` и публикует событие `new_message` в `channel:ticket:{ticket_id}`.
     - **Случай Б (последующие такты планировщика через 30, 60, 90... секунд):**
       - Последнее сообщение в диалоге теперь имеет `sender_type == 'system'`.
       - Условие «последнее сообщение от оператора» **не выполняется**. Предупреждение повторно не отправляется. Спам исключен на 100%.
     - **Случай В (наступление 15 минут — автозакрытие):**
       - Последнее сообщение имеет `sender_type == 'system'`.
       - Возраст этого системного сообщения $\ge 5$ минут (или суммарно прошло $\ge 15$ минут с момента последнего ответа оператора).
       - *Действие:* Тикет переводится в `closed_by_inactivity`, слот оператора освобождается.
     - **Случай Г (клиент написал в чат):**
       - Новое сообщение клиента получает `sender_type == 'client'`.
       - Счетчик сбрасывается естественным образом без каких-либо костылей и очисток флагов.

### Архитектурный вердикт:
Источником правды выступает таблица `messages`. Определение статуса напоминания строится на типе и дате последнего сообщения диалога. Никаких дополнительных колонок в `tickets` и временных ключей в Redis не требуется.

## 2. Гонка между сообщением клиента и автозакрытием (Race Condition)

### Контекст проблемы:
Клиент отправляет сообщение через `POST /api/v1/chat/messages` ровно в ту же миллисекунду, когда воркер Taskiq выполняет фоновое закрытие тикета по таймауту. 
Если воркер выполнит неатомарную последовательность:
1. `SELECT * FROM tickets WHERE status = 'bot_processing' AND updated_at < :cutoff`
2. (В этот момент клиент делает `POST /messages`, пишет сообщение и обновляет `updated_at = now()`)
3. Воркер делает `UPDATE tickets SET status = 'closed_by_inactivity' WHERE id = :id`
Тикет будет ошибочно закрыт, а свежее сообщение клиента останется в закрытом тикете без ответа.

### Решение: Оптимистическая атомарная блокировка на уровне SQL (Conditional UPDATE)
Перевод в статус `closed_by_inactivity` должен выполняться строго с предикатом проверки момента времени:

```sql
UPDATE tickets 
SET status = 'closed_by_inactivity', 
    closed_at = :now, 
    updated_at = :now
WHERE id = :ticket_id 
  AND status = :current_status
  AND updated_at <= :cutoff_timestamp
RETURNING id;
```

### Анализ исходов:
- **Если клиент отправил сообщение до или во время транзакции воркера:**
  Хэндлер клиента уже обновил `updated_at` тикета на текущее время. Условие `updated_at <= :cutoff_timestamp` в запросе воркера вернет `0` обновленных строк (`rowcount == 0`).
  Воркер видит, что тикет обновился, и **отменяет** закрытие: не удаляет контекст из Redis, не освобождает слот оператора и не шлет событие `ticket_closed_inactivity`.
- **Если воркер успел первым:**
  Статус тикета стал `closed_by_inactivity`. Запрос клиента, придя миллисекундой позже, увидит терминальный статус обращения и согласно архитектуре создаст новый активный тикет для продолжения диалога либо вернет понятную ошибку.

### Архитектурный вердикт:
Все операции автозакрытия (`close_inactive_ticket`) обязаны использовать атомарный `UPDATE ... WHERE updated_at <= :cutoff RETURNING id`. Действия в Redis (очистка `chat:context`, публикация Pub/Sub, освобождение слотов) выполняются **только при успешном возврате `id` из запроса**.

## 3. Массовый возврат тикетов оператора (`offline`) и согласованность DB ↔ Redis

### Контекст проблемы:
Оператор закрыл вкладку браузера, связь оборвалась, зафиксирован `disconnected_at`. Через 10 минут планировщик находит сотрудника, у которого зависло 3 тикета (`assigned` или `in_progress`) на линиях L1 и L2.
Необходимо:
1. Перевести статус смены в `offline`, сбросить `disconnected_at = NULL`.
2. Отвязать тикеты от оператора и перевести в `queued`.
3. Поместить тикеты в начало очереди Redis соответствующей линии (`LPUSH queue:line:{line_code}`).
4. Инициировать балансировку.

### Риски и их устранение:

#### 1. Порядок выполнения и сбои (Two-Phase Failure):
- **Правило:** База данных PostgreSQL — строго первична (Single Source of Truth).
- **Сценарий 1:** Сначала выполняется единая транзакция в PostgreSQL:
  ```python
  async with session.begin():
      # 1. Смена статуса оператора
      await operator_repo.set_offline(operator_id)
      # 2. Атомарный перевод тикетов в queued
      requeued_tickets = await operator_repo.requeue_operator_tickets(operator_id)
  ```
  После успешного `commit` транзакции данные в БД гарантированно консистентны.
- **Сценарий 2 (Сбой Redis при LPUSH):**
  Если Redis временно недоступен или сетевой сокет упал, операция `LPUSH` оборачивается в `try/except` с логированием `logger.error(...)`.
  Тикеты не теряются: они уже сохранены в PostgreSQL со статусом `queued`. Встроенный в архитектуру фоновый механизм восстановления очередей (`idx_tickets_queued_recovery`) автоматически подхватит эти тикеты и вернет их в Redis при ближайшей сверке или старте воркера.
- Если бы мы сначала сделали `LPUSH`, а транзакция БД упала — воркер назначил бы тикет, который в БД все еще закреплен за отключенным оператором (рассинхронизация распределения). Поэтому порядок **строго: DB commit -> Redis LPUSH**.

#### 2. Защита от лавины задач (Thundering Herd):
- Если у оператора 3 тикета (2 на линии L1 и 1 на линии L2), наивный код вызовет фоновую задачу `dispatch_line_queue` 3 раза. Две задачи на линии L1 будут конкурировать за `lock:dispatch:line:L1`, порождая лишнюю нагрузку на Redis и брокер.
- **Решение:**
  После возврата тикетов собирается множество уникальных кодов линий:
  ```python
  affected_lines = {t.line.code for t in requeued_tickets if t.line}
  for line_code in affected_lines:
      await broker.find_task("dispatch_line_queue").kiq(
          DispatchPayloadSchema(line_code=line_code, trigger_reason="operator_disconnected")
      )
  ```
  Для каждой затронутой линии запускается **ровно одна** задача диспетчеризации. Так как воркер диспетчера работает в цикле `while True` до исчерпания очереди или свободных слотов, одной задачи на линию исчерпывающе достаточно.

### Архитектурный вердикт:
Строгий порядок: коммит PostgreSQL -> `LPUSH` в Redis -> вызов ровно одной задачи `dispatch_line_queue` на каждую уникальную затронутую линию (`set(line_codes)`).

## 4. Временные зоны и точность сравнения (Clock Skew)

### Контекст проблемы:
- Регламент проекта (`AGENTS.md`): *"проект работает по московскому времени (`Europe/Moscow`, UTC+3). Запрещены хардкод строк таймзон, создание промежуточных переменных-оберток и использование «наивных» дат без часового пояса"*.
- PostgreSQL хранит даты в колонках типа `TIMESTAMPTZ` (UTC на физическом уровне) со значением по умолчанию `clock_timestamp()`.
- В распределенной среде время на сервере базы данных и на нодах с воркерами Taskiq может незначительно расходиться (Clock Skew).

### Инженерное решение:
1. **Генерация меток времени:**
   Все временные пороги формируются строго с часовым поясом настроек проекта:
   ```python
   now = datetime.now(settings.TIMEZONE)
   bot_cutoff = now - timedelta(minutes=10)
   operator_warn_cutoff = now - timedelta(minutes=10)
   operator_close_cutoff = now - timedelta(minutes=15)
   operator_disconnect_cutoff = now - timedelta(minutes=10)
   ```
2. **Параметризация репозиториев для детерминированного тестирования:**
   Методы репозитория обязаны принимать `cutoff` (или `now`) опциональным аргументом:
   ```python
   async def get_inactive_bot_tickets(
       self, 
       cutoff: datetime | None = None,
       limit: int = 100,
   ) -> list[TicketModel]:
       if cutoff is None:
           cutoff = datetime.now(settings.TIMEZONE) - timedelta(minutes=10)
       ...
   ```
   Это гарантирует, что в unit-тестах можно легко передавать замороженные или сдвинутые метки времени без необходимости мокать системные часы операционной системы или базу данных.
3. **Совместимость драйвера asyncpg:**
   `asyncpg` нативно поддерживает timezone-aware объекты Python `datetime` и передает их в PostgreSQL с точным смещением, исключая любые искажения при сравнении с `TIMESTAMPTZ`.

### Архитектурный вердикт:
Использование `datetime.now(settings.TIMEZONE)` для вычисления границ отсечения `:cutoff`, передача явных параметров в методы репозиториев для поддержки легкого тестирования.

## 5. Поведение распределенного лока (`RedisDistributedLock`)

### Контекст проблемы:
Планировщик запускает задачу `check_system_timeouts` каждые 30 секунд.
Блокировка `lock:check_system_timeouts` создается с TTL 25 секунд.
Если база данных окажется под аномальной нагрузкой (например, тяжелый аналитический отчет заблокировал таблицы), и выполнение задачи займет 26 секунд:
1. Через 25 секунд ключ в Redis удалится по TTL.
2. Через 30 секунд планировщик запустит следующий такт `check_system_timeouts`.
3. Второй воркер успешно захватит ключ `lock:check_system_timeouts`.
4. В системе окажутся два параллельно работающих процесса `check_system_timeouts`.
5. Первый воркер, завершив работу на 26-й секунде, вызовет `release()`.

### Анализ рисков и защита:

1. **Защита от чужого освобождения (Safe Release):**
   В существующем классе `RedisDistributedLock` уже заложен Lua-скрипт:
   ```lua
   if redis.call("get", KEYS[1]) == ARGV[1] then
       return redis.call("del", KEYS[1])
   else
       return 0
   end
   ```
   Первый воркер передаст свой UUID токена. Ключ в этот момент либо пуст, либо содержит токен второго воркера. Lua-скрипт вернет 0 и **не удалит чужой лок**. Каскадного разрушения блокировок не произойдет.

2. **Локальный превентивный таймаут (`asyncio.timeout`):**
   Чтобы выполнение бизнес-логики в принципе не могло перевалить за TTL блокировки, выполнение тела задачи оборачивается в строгий асинхронный таймаут 20 секунд:
   ```python
   async with lock as acquired:
       if not acquired:
           logger.info("Задача check_system_timeouts уже выполняется другим воркером, пропуск")
           return
       try:
           async with asyncio.timeout(20.0):
               await operator_service.check_timeouts()
       except TimeoutError:
           logger.error("Таймаут выполнения check_system_timeouts (превышено 20с), операция прервана")
   ```
   Так как `20с < TTL (25с) < Interval (30с)`, задача всегда либо корректно завершится и снимет свой лок, либо принудительно прервется по `TimeoutError` за 5 секунд до истечения срока жизни ключа в Redis. Параллельный запуск двух инстансов математически исключен.

3. **Батчинг запросов (`LIMIT 100`):**
   Выборка зависших сущностей не должна сканировать всю базу:
   Все запросы снабжаются лимитом `LIMIT 100` на каждый тип проверки. Если в системе скопилось 500 зависших тикетов, они будут безопасно закрыты за 5 последовательных тактов по 30 секунд без пиковых нагрузок на БД.

### Архитектурный вердикт:
Жесткое ограничение времени выполнения `asyncio.timeout(20.0)` внутри задачи при TTL лока 25 с и интервале планировщика 30 с полностью предотвращает наложение воркеров. Пакетная обработка (`LIMIT 100`) исключает деградацию запросов к БД.
