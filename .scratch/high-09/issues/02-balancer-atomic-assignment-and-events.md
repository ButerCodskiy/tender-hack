# 02: Балансировщик обращений, атомарный выбор оператора и шина событий

**What to build:** Механизм атомарного распределения тикетов из очереди на наименее загруженного доступного специалиста линии и мгновенное оповещение оператора через шину событий.

**Blocked by:** 01: Профиль оператора, миграция базы данных и приоритетная очередь в Redis

**Status:** closed

- [x] Реализован атомарный выбор наименее загруженного активного оператора для заданной линии поддержки: оператор находится в статусе смены `active`, соединение активно (`disconnected_at IS NULL`), число текущих активных слотов в статусах `assigned` и `in_progress` строго меньше `max_slots`.
- [x] Приоритет при выборе оператора отдается специалисту с наименьшим числом занятых слотов; при равной загрузке выбирается оператор с наиболее давней меткой `last_assigned_at` (или `NULL`).
- [x] Выбор оператора защищен от состояния гонки блокировкой строки в базе данных (`FOR UPDATE`).
- [x] При успешном сопоставлении статус тикета в базе данных переводится в `assigned`, заполняется поле `assigned_operator_id`, фиксируется `assigned_at`, а в профиле оператора обновляется `last_assigned_at` в рамках единой транзакции.
- [x] Реализована публикация события назначения тикета в канал Redis Pub/Sub `channel:operator:{operator_id}` для оперативного обновления рабочего места специалиста.
- [x] Написаны интеграционные тесты, проверяющие корректность выбора наименее загруженного оператора при конкурентных обращениях и доставку события в шину Pub/Sub.
