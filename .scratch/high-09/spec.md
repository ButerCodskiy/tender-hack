# Спецификация: [HIGH-09] Балансировщик обращений, распределение слотов и очереди ожидания

## 1. Цель
Реализовать доменный механизм буферизации, балансировки и назначения обращений клиентов на операторов службы поддержки в соответствии со спецификацией очередей (`docs/QUEUES_SPECIFICATION.md`), схемой базы данных (`docs/DATABASE_SPECIFICATION.md`) и архитектурой бэкенда (`docs/BACKEND_ARCHITECTURE.md`).

## 2. Основные требования

### 2.1. Слой данных и профили операторов (PostgreSQL)
1. **Профиль оператора (`operator_profiles` / `OperatorProfileModel`):**
   * Размещается в `src/operators/models.py`.
   * Первичный ключ `user_id` (`UUID`, внешний ключ к `users.id` с каскадным удалением).
   * Внешний ключ `line_id` (`SmallInteger`, ссылка на `support_lines.id`).
   * Статус смены `shift_status`: `active`, `break`, `offline` (по умолчанию `offline`).
   * Лимит параллельных диалогов `max_slots` (`SmallInteger`, по умолчанию 5, от 1 до 20).
   * Метки времени: `disconnected_at` (фиксация разрыва связи), `last_assigned_at` (время последнего назначения), `updated_at`.
   * Индекс `idx_operator_profiles_dispatch` на `(line_id, shift_status)` для фильтрации активных операторов.
2. **Репозиторий операторов (`OperatorRepository`):**
   * Размещается в `src/operators/repository.py`.
   * Методы создания и получения профиля оператора, смены статуса смены, выборки активных специалистов.

### 2.2. Буферизация очередей ожидания (Redis)
1. Для каждой линии поддержки в Redis ведется список `queue:line:{line_code}`.
2. При добавлении тикета учитывается приоритет:
   * P0 (критический) добавляется в начало очереди командой `LPUSH`.
   * P1 и P2 добавляются в конец очереди командой `RPUSH`.
3. Извлечение обращений выполняется с начала очереди командой `LPOP`.

### 2.3. Алгоритм балансировки и назначение
1. Атомарный выбор наименее загруженного сотрудника в PostgreSQL:
   * Статус смены: `shift_status = 'active'`, `disconnected_at IS NULL`.
   * Число текущих обращений в статусах `assigned` и `in_progress` строго меньше `max_slots`.
   * Сортировка по возрастанию занятых слотов (`active_slots ASC`), а при равенстве — по давности предыдущего назначения (`last_assigned_at ASC NULLS FIRST`).
   * Блокировка строки оператора через `FOR UPDATE OF op`.
2. Фиксация назначения:
   * Статус тикета переводится в `assigned`, устанавливается `assigned_operator_id`, фиксируются `assigned_at` и `updated_at`.
   * В `operator_profiles` обновляется `last_assigned_at`.
3. Публикация события в канал `channel:operator:{operator_id}` через Redis Pub/Sub для оповещения рабочего места сотрудника.

### 2.4. Фоновая задача и координация (Taskiq)
1. Задача `dispatch_line_queue` регистрируется в очереди `dispatch_queue`.
2. Контракт нагрузки `DispatchPayloadSchema` содержит `line_code` и `trigger_reason`.
3. Распределение защищено распределенной блокировкой `lock:dispatch:line:{line_code}` с временем жизни 5 секунд и освобождением через Lua-скрипт с проверкой идентификатора воркера.
