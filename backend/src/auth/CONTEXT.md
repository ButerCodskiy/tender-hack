# Доменный контекст: Auth

## Назначение
Управление учетными записями, аутентификацией, ролями пользователей и организациями.

## Обязательные спецификации и источник истины
Код и интерфейсы модуля должны строго следовать утвержденным спецификациям проекта. Агентам запрещено отклоняться от согласованных схем, эндпоинтов и моделей без оформления архитектурного решения в `docs/adr/`:
- **Архитектура аутентификации**: [docs/BACKEND_ARCHITECTURE.md](../../../docs/BACKEND_ARCHITECTURE.md) (раздел 6: схема JWT, валидация прав, авторизация в SSE).
- **Контракты API v1**: [docs/API_SPECIFICATION.md](../../../docs/API_SPECIFICATION.md) (раздел 2: эндпоинты `/api/v1/auth/*`, схемы запросов и ответов).
- **Схема базы данных**: [docs/DATABASE_SPECIFICATION.md](../../../docs/DATABASE_SPECIFICATION.md) (раздел 2: таблицы `users`, `roles`, `organizations`).
- **Схема структуры и импортов**: [docs/PROJECT_STRUCTURE.md](../../../docs/PROJECT_STRUCTURE.md) (матрица допустимых зависимостей).

## Сущности и термины
- **Пользователь (User / `UserModel`)**: учетная запись в системе с электронной почтой, хешем пароля и профилем.
- **Роль (Role / `RoleModel`)**: системная роль пользователя (`client`, `operator`, `supervisor`, `admin`).
- **Организация (Organization / `OrganizationModel`)**: юридическое лицо или клиентская организация.

## Границы и правила
- Пароли хранятся исключительно в виде криптографических хешей.
- Аутентификация выполняется через пару токенов: кратковременный access-токен (15 минут) и refresh-токен (7 дней).
- Роли разграничивают доступ к маршрутам API и операциям.
