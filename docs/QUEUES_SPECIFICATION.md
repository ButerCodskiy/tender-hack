# Спецификация асинхронных очередей и фоновых задач

Документ определяет архитектуру очередей Taskiq, схемы полезной нагрузки фоновых задач, логику распределения обращений и регламенты обработки отложенных событий.

---

## 1. Архитектура фоновой обработки и топология очередей

Система фоновой обработки изолирует длительные вычислительные операции и сетевые запросы от основного HTTP-цикла FastAPI, гарантируя высокую скорость отклика интерфейса.

### Технологический базис

* **Фреймворк фоновых задач:** Taskiq. Воркеры функционируют непосредственно в цикле событий asyncio, исключая накладные расходы при взаимодействии с асинхронным драйвером базы данных asyncpg.
* **Брокер сообщений:** Redis 7. Обеспечивает буферизацию задач, хранение оперативных очередей тикетов и межпроцессную координацию через распределенные блокировки.
* **Планировщик периодических задач:** Taskiq Scheduler. Отвечает за запуск регулярных проверок неактивности, контроль связи операторов и сверку зависших очередей.
* **Единый источник состояния:** PostgreSQL 16. Все долговременные изменения статусов, результаты аналитики и фиксация ошибок сохраняются в реляционной базе данных.

### Реестр очередей Taskiq

Задачи сгруппированы по четырем изолированным очередям в зависимости от характера нагрузки и требований к скорости выполнения.

| Название очереди | Назначение | Критичность к задержке | Предельный таймаут | Параллелизм воркера |
|---|---|---|---|---|
| `dispatch_queue` | Распределение тикетов между операторами | Критическая (доли секунды) | 10 секунд | Высокий (I/O) |
| `copilot_queue` | Генерация подсказок и подбор статей для оператора | Высокая (1–4 секунды) | 30 секунд | Средний (Network I/O) |
| `analytics_queue` | Аудит закрытых диалогов языковой моделью, расчет метрик | Средняя (секунды, минуты) | 120 секунд | Умеренный (LLM API) |
| `ingestion_queue` | Парсинг файлов, нарезка на фрагменты, расчет векторов | Низкая (минуты) | 600 секунд | Ограниченный (CPU/Disk) |

## 2. Спецификация задач и контракты полезной нагрузки

Все сообщения в очередях передаются в формате JSON. Контракты данных строго типизированы и содержат только необходимые идентификаторы сущностей.

### 2.1. Очередь распределения обращений (`dispatch_queue`)

#### Задача `dispatch_line_queue`
Инициирует сопоставление ожидающих тикетов со свободными слотами операторов соответствующей линии.
* **Исполняющий доменный сервис:** `OperatorService.dispatch_line()` в `src/operators/service.py`.
* **Схема полезной нагрузки:** `DispatchPayloadSchema` в `src/operators/schemas.py`.

* **Точки вызова:**
  * Эскалация обращения от бота или перевод на оператора (`status = 'queued'`).
  * Освобождение слота специалиста (завершение диалога, перевод на другую линию, выход с перерыва).
  * Резервная периодическая сверка планировщиком Taskiq Scheduler раз в 30 секунд.
* **Формат полезной нагрузки (`DispatchPayloadSchema`):**
  ```json
  {
    "line_code": "L1",
    "trigger_reason": "ticket_escalated"
  }
  ```
* **Поля полезной нагрузки:**
  * `line_code` (`string`, обязательное): системный код линии поддержки (`L1`, `L2`, `L3`).
  * `trigger_reason` (`string`, обязательное): причина запуска (`ticket_escalated`, `slot_freed`, `shift_resumed`, `scheduled_sync`).
* **Базовый сценарий исполнения:**
  1. Захватывается распределенная блокировка `lock:dispatch:line:{line_code}` в Redis с временем жизни 5 секунд. При невозможности захвата задача завершается (распределение уже выполняется параллельным процессом).
  2. Проверяется наличие тикетов в списке `queue:line:{line_code}`. Если очередь пуста, блокировка снимается, задача завершается.
  3. В транзакции PostgreSQL выполняется атомарный поиск наименее загруженного активного оператора с доступными слотами (`active_slots < max_slots`).
  4. При нахождении оператора первый идентификатор тикета извлекается из Redis (`LPOP`), статус тикета в базе данных переводится в `assigned`, обновляется метка `last_assigned_at` сотрудника.
  5. Отправляется уведомление в канал `channel:operator:{operator_id}` через Redis Pub/Sub для мгновенного появления тикета в сайдбаре специалиста.
  6. Распределенная блокировка снимается.

### 2.2. Очередь подсказок для оператора (`copilot_queue`)

#### Задача `generate_copilot_summary`
Формирует смысловую выжимку проблемы клиента и подбирает релевантные нормативные статьи базы знаний через модуль `rag/copilot.py`.
* **Исполняющий доменный сервис:** `RagService.generate_copilot_summary()` в `src/rag/service.py`.
* **Схема полезной нагрузки:** `CopilotPayloadSchema` в `src/rag/schemas.py`.

* **Точки вызова:**
  * Перевод обращения в статус `queued` при эскалации к оператору.
  * Ручной перевод тикета на другую линию поддержки.
* **Формат полезной нагрузки (`CopilotPayloadSchema`):**
  ```json
  {
    "ticket_id": "6a1c5b8e-3d2f-4a1b-9c8e-7f6e5d4c3b2a"
  }
  ```
* **Поля полезной нагрузки:**
  * `ticket_id` (`UUID`, обязательное): уникальный идентификатор обращения.
* **Базовый сценарий исполнения:**
  1. Воркер считывает последние реплики обращения из PostgreSQL или оперативного контекста Redis (`chat:context:{ticket_id}`).
  2. Вызывается фасад модуля `rag/copilot.py` с легковесным обращением к языковой модели.
  3. Формируется структурированный результат: краткое резюме вопроса (`summary`), список ссылок на статьи базы знаний (`recommended_chunk_ids`), похожие закрытые обращения специалистов со статусом `resolved` (с участием оператора: `assigned_operator_id IS NOT NULL`) из коллекции `resolved_tickets` в Qdrant (`similar_resolved_tickets`) и черновик ответа (`suggested_response`).
  4. Данные сохраняются в таблицу `ticket_copilot_summaries` со связью к тикету.
  5. В канал оператора `channel:operator:{operator_id}` отправляется системное событие `copilot_ready` через Redis Pub/Sub. Если оператор к этому моменту уже открыл карточку обращения, интерфейс подтягивает подсказку на лету без перезагрузки страницы.

### 2.3. Очередь аналитики и контроля качества (`analytics_queue`)

#### Задача `audit_ticket_quality`
Выполняет автоматическую проверку качества диалога и арбитраж негативных оценок клиентов.
* **Исполняющий доменный сервис:** `AnalyticsService.audit_ticket()` в `src/analytics/service.py`.
* **Схема полезной нагрузки:** `AuditTicketPayloadSchema` в `src/analytics/schemas.py`.

* **Точки вызова:**
  * Сохранение отзыва клиента в таблице `ticket_feedbacks`.
  * Истечение 10 минут ожидания отзыва после закрытия обращения (запуск планировщиком).
* **Формат полезной нагрузки (`AuditTicketPayloadSchema`):**
  ```json
  {
    "ticket_id": "6a1c5b8e-3d2f-4a1b-9c8e-7f6e5d4c3b2a",
    "trigger_reason": "feedback_received"
  }
  ```
* **Поля полезной нагрузки:**
  * `ticket_id` (`UUID`, обязательное): уникальный идентификатор тикета.
  * `trigger_reason` (`string`, обязательное): источник запуска (`feedback_received` или `feedback_timeout`).
* **Базовый сценарий исполнения:**
  1. Воркер проверяет наличие записи в таблице `ticket_audits`. При ее наличии задача завершается для исключения повторного анализа.
  2. Загружается полная история сообщений тикета и текст отзыва клиента при наличии.
  3. Языковая модель формирует структурированную оценку: баллы вежливости (1–5), полноты ответа (1–5) и флаг системного сбоя платформы.
  4. Результаты сохраняются в таблицу `ticket_audits`.
  5. При фиксации системного сбоя портала запись автоматически добавляется в реестр `system_incidents`, а негативная оценка клиента исключается из расчета показателей специалиста.

#### Задача `calculate_daily_metrics`
Выполняет агрегацию ключевых показателей эффективности операторов за прошедшие сутки.
* **Исполняющий доменный сервис:** `AnalyticsService.calculate_daily_metrics()` в `src/analytics/service.py`.
* **Схема полезной нагрузки:** `DailyMetricsPayloadSchema` в `src/analytics/schemas.py`.

* **Точки вызова:**
  * Расписание Taskiq Scheduler: ежедневно в 00:05.
* **Формат полезной нагрузки (`DailyMetricsPayloadSchema`):**
  ```json
  {
    "metric_date": "2026-09-06",
    "operator_id": null
  }
  ```
* **Поля полезной нагрузки:**
  * `metric_date` (`string` в формате YYYY-MM-DD, обязательное): дата расчетного периода.
  * `operator_id` (`UUID`, опциональное): идентификатор конкретного сотрудника для точечного перерасчета. При значении `null` расчет выполняется по всем операторам смены.
* **Базовый сценарий исполнения:**
  1. Выполняются агрегирующие SQL-запросы по закрытым тикетам за указанную дату: подсчет общего числа обращений, среднего времени первого ответа, времени обработки и скорректированной оценки удовлетворенности.
  2. Результаты атомарно фиксируются в таблице `operator_metrics_daily` с разрешением конфликтов по составному ключу сотрудника и даты.

### 2.4. Очередь индексации базы знаний (`ingestion_queue`)

#### Задача `index_kb_document`
Выполняет первичный парсинг, структурный разбор документа, нарезку на смысловые фрагменты и сохранение векторных представлений.
* **Исполняющий доменный сервис:** `KbService.index_document()` в `src/kb/service.py`.
* **Схема полезной нагрузки:** `IndexDocumentPayloadSchema` в `src/kb/schemas.py`.

* **Точки вызова:**
  * Загрузка файла администратором через эндпоинт `POST /api/v1/kb/documents/upload`.
* **Формат полезной нагрузки (`IndexDocumentPayloadSchema`):**
  ```json
  {
    "document_id": "kb_doc_fed_law_44_v1",
    "file_path": "uploads/kb/doc_44_fz.pdf"
  }
  ```
* **Поля полезной нагрузки:**
  * `document_id` (`string`, обязательное): идентификатор записи документа в PostgreSQL.
  * `file_path` (`string`, обязательное): путь к сохраненному файлу на общем дисковом томе.
* **Базовый сценарий исполнения:**
  1. Статус документа в таблице `kb_documents` переводится в `indexing`.
  2. Модуль парсинга производит извлечение текста, таблиц и структуры заголовков.
  3. Текст разбивается на смысловые фрагменты, создаются записи в таблицах `kb_nodes` и `kb_chunks`.
  4. Вычисляются плотные и разреженные векторные представления фрагментов.
  5. Векторы сохраняются в хранилище Qdrant, а метаданные связываются с реляционными сущностями.
  6. Статус документа в таблице `kb_documents` обновляется на `indexed`. При ошибке статус переводится в `failed` с фиксацией причины в `error_message`.
  7. При успешной индексации ставится вторичная задача `enrich_kb_chunks` для контекстуализации фрагментов.

#### Задача `enrich_kb_chunks`
Выполняет асинхронное обогащение текстовых фрагментов контекстными префиксами и гипотетическими вопросами без блокировки базового поиска.
* **Исполняющий доменный сервис:** `KbService.enrich_chunks()` в `src/kb/service.py`.
* **Схема полезной нагрузки:** `EnrichChunksPayloadSchema` в `src/kb/schemas.py`.

* **Точки вызова:**
  * Автоматически по завершении задачи `index_kb_document`.
* **Формат полезной нагрузки (`EnrichChunksPayloadSchema`):**
  ```json
  {
    "document_id": "kb_doc_fed_law_44_v1"
  }
  ```
* **Поля полезной нагрузки:**
  * `document_id` (`string`, обязательное): идентификатор проиндексированного документа.
* **Базовый сценарий исполнения:**
  1. Извлекаются фрагменты документа, не имеющие контекстного префикса.
  2. Языковая модель генерирует поясняющий контекст и вероятные поисковые формулировки пользователей.
  3. Значения записываются в колонки `context_prefix` и `hyp_questions` таблицы `kb_chunks`.
  4. Обновленные векторы синхронизируются с Qdrant.

## 3. Регламент работы балансировщика и очередей ожидания

Очередь ожидания специалистов строится на комбинации упорядоченных списков Redis и атомарных транзакций PostgreSQL.

### Приоритеты обращений и целевые нормативы SLA

Балансировщик и логика распределения тикетов строго дифференцируют обращения по приоритету для соблюдения нормативов времени ожидания ответа:
* **P0 (Блокирующий / Критический, SLA < 60 с):** критические инциденты в день окончания подачи заявок (< 24 часов), сбои подписания ЭЦП, блокировка обеспечения заявок, угроза срыва регламентных сроков.
* **P1 (Высокий, SLA < 180 с):** ошибки криптографических плагинов (`0x...`), технические сбои личного кабинета, эскалации со специализированных линий.
* **P2 (Стандартный, SLA < 600 с):** консультации по регламенту и функционалу площадки, типовые вопросы первой линии.

### Логика балансировщика и выборка из базы данных

Балансировщик распределения тикетов и процедуры восстановления очередей из PostgreSQL учитывают приоритет обращения:
* **Сортировка очереди в БД:** при выборке тикетов из PostgreSQL (при стартовом холодном перезапуске, восстановлении очередей и плановой сверке зависших тикетов раз в 30 секунд) всегда применяется строгая сортировка:
  ```sql
  SELECT id, line_id, priority, created_at
  FROM tickets
  WHERE status = 'queued'
  ORDER BY priority ASC, created_at ASC;
  ```
  Индекс `idx_tickets_queued_recovery` на `(line_id, priority, created_at)` обеспечивает моментальную выборку без сканирования всей таблицы. Поскольку `'P0' < 'P1' < 'P2'`, критические тикеты первыми поступают на распределение, а внутри одного приоритета сохраняется хронологический порядок поступления (FIFO).

### Управление списками ожидания в Redis

Для каждой линии поддержки в Redis поддерживается собственный список: `queue:line:{line_code}`.
* **Добавление с учетом приоритета:** критические тикеты P0 помещаются в начало очереди командой `LPUSH queue:line:{line_code}` для мгновенного назначения первому освободившемуся оператору (соблюдение SLA < 60 с). Тикеты стандартных приоритетов P1 и P2 добавляются в конец очереди командой `RPUSH queue:line:{line_code}`.
* **Извлечение из начала очереди (`LPOP`):** обеспечивает непрерывное обслуживание обращений с головы очереди.
* **Приоритетный возврат в начало очереди (`LPUSH`):** применяется при аварийном разрыве связи оператора (таймаут более 10 минут) для возврата незавершенных обращений в приоритетное обслуживание.

### Защита от состояния гонки

Процедура распределения для конкретной линии всегда защищается распределенной блокировкой:
`SET lock:dispatch:line:{line_code} "{worker_uuid}" NX EX 5`
* Если ключ заблокирован другим воркером, повторный запуск пропускается без ошибок.
* Снятие блокировки выполняется атомарным скриптом Lua с проверкой совпадения идентификатора владельца блокировки (`worker_uuid`).

## 4. Контроль отложенных событий и таймаутов

Все временные ограничения в системе контролируются централизованной сервисной задачей `check_system_timeouts` (исполняющий доменный сервис: `OperatorService.check_timeouts()` в `src/operators/service.py`), запускаемой планировщиком Taskiq Scheduler каждые 30 секунд. 

Использование периодической сверки базы данных исключает накопление тысяч неактуальных отложенных сообщений в брокере и автоматически восстанавливает консистентность системы после перезапуска серверов.

```
+-----------------------------------------------------------------------------+
|               Taskiq Scheduler (раз в 30 секунд)                            |
|                       Задача check_system_timeouts                          |
+-------------------------------------+---------------------------------------+
                                      |
       +------------------------------+------------------------------+
       |                              |                              |
       v                              v                              v
[1. Неактивность клиентов]    [2. Контроль операторов]      [3. Сбор аналитики]
- 10 мин без ответа у бота:   - Отключение > 10 мин:        - Тикет закрыт > 10 мин
  status = closed_by_inactivity status = offline             без отзыва клиента:
- 10 мин у оператора:         - Возврат тикетов в LPUSH      отправка в analytics_queue
  напоминание в чат             queue:line:{line_code}       (audit_ticket_quality)
- 15 мин у оператора:         - Запуск dispatch_line_queue
  status = closed_by_inactivity
  освобождение слота
```

### Регламенты проверок

1. **Неактивность клиента в диалоге с ботом (10 минут):**
   * Критерий выборки: `status = 'bot_processing' AND updated_at < clock_timestamp() - interval '10 minutes'`.
   * Действие: тикет переводится в статус `closed_by_inactivity`, удаляется оперативный контекст `chat:context:{ticket_id}` в Redis, клиенту отправляется системное сообщение о завершении сессии.
2. **Неактивность клиента в диалоге с оператором (10 и 15 минут):**
   * Критерий первого предупреждения: `status = 'in_progress' AND last_message_sender = 'operator' AND updated_at < clock_timestamp() - interval '10 minutes'` при отсутствии флага отправленного предупреждения.
   * Действие первого шага: отправка в чат сервисного напоминания «Вы еще здесь?».
   * Критерий закрытия: отсутствие сообщений клиента в течение 15 минут суммарно.
   * Действие второго шага: тикет переводится в статус `closed_by_inactivity`, рабочий слот оператора освобождается, инициируется задача `dispatch_line_queue` для назначения следующего клиента.
3. **Контроль разрыва соединения оператора (10 минут):**
   * При закрытии вкладки или браузера постоянное соединение GET SSE обрывается, обработчик FastAPI в блоке `finally` фиксирует точное время: `disconnected_at = clock_timestamp()`.
   * Критерий тайм-аута: `shift_status = 'active' AND disconnected_at < clock_timestamp() - interval '10 minutes'`.
   * Действие: статус сотрудника переводится в `offline`, поле `disconnected_at` сбрасывается в `NULL`. Все незавершенные тикеты сотрудника со статусами `assigned` и `in_progress` переводятся в статус `queued`, отвязываются от оператора и помещаются в начало очереди Redis соответствующей линии командой `LPUSH queue:line:{line_code}`. Сразу вызывается задача распределения очереди.
4. **Запуск контроля качества без отзыва клиента (10 минут):**
   * Критерий выборки: `status = 'resolved' AND closed_at < clock_timestamp() - interval '10 minutes'` при отсутствии записи в `ticket_audits` и отсутствии отзыва в `ticket_feedbacks` (в первую очередь анализируются тикеты с участием человека: `assigned_operator_id IS NOT NULL`).
   * Действие: обращение отправляется на автоматическую проверку постановкой задачи `audit_ticket_quality` в очередь `analytics_queue`.

## 5. Политика повторов, таймауты исполнения и обработка сбоев

### Параметры надежности очередей

| Очередь | Максимум попыток | Стратегия задержки повторов | Таймаут задачи | Поведение при фатальном сбое |
|---|---|---|---|---|
| `dispatch_queue` | 2 | Фиксированная (1 секунда) | 10 секунд | Запись в лог; тикет остается в очереди Redis до плановой сверки |
| `copilot_queue` | 2 | Фиксированная (3 секунды) | 30 секунд | Запись ошибки в `ticket_copilot_summaries`, оператор работает без подсказки |
| `analytics_queue` | 3 | Экспоненциальная (5с, 15с, 45с) | 120 секунд | Создание записи инцидента в таблице `system_incidents` |
| `ingestion_queue` | 2 | Фиксированная (10 секунд) | 600 секунд | Документ переводится в статус `failed` с текстом ошибки в `kb_documents` |

### Регламент фиксации фатальных ошибок

Вместо использования скрытых очередей отбракованных сообщений все окончательные сбои фиксируются в реляционных сущностях, доступных административному интерфейсу:
* **Сбои парсинга и векторизации:** документ в таблице `kb_documents` получает статус `failed`, а точный текст исключения записывается в колонку `error_message`. Администратор видит ошибку в панели управления и может инициировать повторную обработку после исправления файла.
* **Сбои контроля качества:** при троекратном сбое вызова языковой модели в таблицу `system_incidents` добавляется запись с кодом сбоя `analytics_failure` и идентификатором тикета.
* **Сбои генерации подсказки:** не прерывают обслуживание клиента. В таблицу подсказок пишется статус `failed`, а интерфейс оператора скрывает блок подсказки, позволяя ответить по общим регламентам.

## 6. Краевые случаи и аварийное восстановление

* **Аварийный перезапуск или сброс Redis:**
  При потере оперативных данных в Redis стартовый обработчик бэкенда восстанавливает очереди ожидания прямым запросом к PostgreSQL:
  ```sql
  SELECT t.id, sl.code AS line_code
  FROM tickets t
  JOIN support_lines sl ON sl.id = t.line_id
  WHERE t.status = 'queued'
  ORDER BY t.created_at ASC;
  ```
  Идентификаторы пакетом загружаются в соответствующие ключи `queue:line:{line_code}` командой `RPUSH`, восстанавливая целостность очередей без потери клиентов.
* **Зависание распределенной блокировки:**
  Жесткое время жизни ключа блокировки 5 секунд исключает блокировку очередей при внезапном падении процесса воркера во время распределения.
* **Идемпотентность фоновых задач:**
  Все задачи очередей содержат проверки актуальности текущего состояния сущности перед записью в базу данных. Повторное получение сообщения воркером не приводит к дублированию назначений или повторному созданию записей аудита.
