# Архитектурная спецификация серверной части: RAG, АРМ оператора, аналитика и Data Flywheel (Версия 6.2 Frozen)

Область применения: техническое задание для бэкенд-разработки; API-контракт АРМ/дашборда — отдельный документ [API_CONTRACT.md](./API_CONTRACT.md) (см. Раздел 12).

Регламент проектирования поискового конвейера, автоматизированных рабочих мест поддержки, аналитики и контура самообучения базы знаний.

## 0. Исходные данные и допущения

1. **Характер и состав корпуса:**
   * **Основной корпус (`kb_type = 'guide'`):** Официальные руководства пользователей, пошаговые инструкции, регламенты Портала поставщиков Москвы (`zakupki.mos.ru`), предоставляемые организаторами хакатона. Форматы файлов организаторов вариативны: PDF, DOCX, HTML, XLSX, CSV, включая возможное наличие графических сканов документов.
   * **Дополнительный слой нормативных актов (`kb_type = 'regulation'`):** Федеральное законодательство (44-ФЗ, 223-ФЗ) и постановления Правительства Москвы, регламентирующие порядок электронных закупок.
   * **База типовых решений и FAQ (`kb_type = 'faq'`):** Официальные таблицы «вопрос-ответ» организаторов и промодерированные решения из контура самообучения.
   * **Техническая база знаний (`kb_type = 'tech'`):** Справочники кодов ошибок (0x...), инструкции к плагинам ЭЦП (КриптоПро) и совместимости браузеров.
2. **Особенности адресации документов:**
   * Механизмы поиска по статьям, частям и пунктам (пре-роутер, поля `article_no`, `part_no`) являются опциональными и активируются исключительно для документов уровня законодательных актов (`kb_type = 'regulation'`).
   * Для методичек, регламентов и пользовательских инструкций портала (`kb_type = 'guide'`) основным маршрутом структурирования и поиска является путь по дереву документа `section_path` (Раздел $\to$ Подраздел $\to$ Пункт), формируемый по абстрактному синтаксическому дереву (AST).
3. **Обработка структурированных таблиц FAQ (XLSX / CSV) и синтетические узлы:**
   * При предоставлении организаторами готовых таблиц вопросов и ответов в форматах XLSX или CSV данные загружаются напрямую в базу с признаками `kb_type = 'faq'` и `kind = 'qa_pair'` в обход модуля разбора Docling.
   * Для сохранения ссылочной целостности внешнего ключа `chunks.node_id REFERENCES nodes(node_id)` создается синтетическая запись в таблице `documents` (`doc_id = 'DOC_FAQ_' || hash`, `title` = имя исходного файла, `regime = 'MOS_PORTAL'`) и синтетический узел в таблице `nodes` (`node_id = 'NODE_FAQ_' || hash`, `level = 'item'`, `section_path = 'FAQ Import'`, `title` = вопрос).
   * Готовые пары «вопрос-ответ» организаторов индексируются на старте системы до запуска контура самообучения.
4. **Регламент приема корпуса в день хакатона:**
   * Запуск пакетной обработки выполняется консольной командой `ingest --dir <folder>` с параллельным выполнением задач.
   * По каждому файлу формируется отчет полноты извлечения текста; файлы с расхождением объема более 5% помещаются в перечень для ручной проверки.
   * Целевое время полной базовой индексации корпуса организаторов составляет `[MEASURE]` с целевым нормативом $\le 60$ минут.
   * **Двухфазная индексация:** Базовый поиск по плотным (`dense`) и разреженным (`sparse`) векторам доступен пользователям сразу после завершения первичного парсинга Docling (в таблице `chunks` поле `context_prefix TEXT NULL`). Контекстуализация (`context_prefix`) и генерация гипотетических вопросов (`hyp_questions`) выполняются асинхронным воркером `Taskiq` в фоновом режиме. После формирования префикса воркер инициирует re-embedding точки и re-upsert обновленного вектора в Qdrant.
5. **Поставляемый артефакт «Структурированная база знаний»:**
   * Пользовательский интерфейс и программный эндпоинт «База знаний» предоставляют интерактивное дерево `documents` $\to$ `nodes` с путями `section_path`, окном просмотра содержимого чанка, метаданными и признаком `kb_type`.
   * Реализован экспорт всей структурированной базы знаний в единый архив формата JSON и структурированное дерево файлов Markdown для передачи организаторам.
   * Обеспечен вывод сводной статистики: общее число документов, иерархических узлов, чанков, таблиц и пар типовых вопросов.

## 1. Компонентный стек подсистемы и аппаратная конфигурация

| Уровень архитектуры | Выбранное решение | Назначение и критерий выбора |
|---|---|---|
| Парсинг документов | Docling (TableFormer, встроенный RapidOCR) | Извлечение структуры AST, сеток таблиц и чтение сканов без потери колонок |
| Валидация объема | PyMuPDF | Потоковое сравнение объема символов для контроля полноты выгрузки Docling |
| Прямой парсинг FAQ | openpyxl / csv | Прямой разбор структурированных таблиц вопросов и ответов организаторов с генерацией синтетических узлов |
| Чанкинг и метаданные | Иерархический по AST Docling | Нарезка по структурным границам статей и пунктов с лимитом до 350 токенов |
| Плотные векторы (Dense) | BAAI/bge-m3 (профиль по умолчанию) | 1024-мерные векторные представления текста с поддержкой русского языка |
| Разреженные векторы (Sparse) | BM25 через fastembed | Лексический поиск с русским Snowball-стеммером для точных совпадений |
| Векторная база данных | Qdrant | Единая коллекция knowledge_base (фильтр по `kb_type IN ('regulation', 'guide', 'faq', 'tech')`) и коллекция resolved_tickets |
| Сервинг моделей поиска | TEI (Text Embeddings Inference) | Батчинг и сервинг bge-m3 и bge-reranker-v2-m3 на локальном GPU (16 ГБ VRAM) |
| Реранкинг кандидатов | BAAI/bge-reranker-v2-m3 | Cross-Encoder перепроверка 40 кандидатов первичного поиска через TEI |
| Первичное хранилище (Docstore) | PostgreSQL | Хранение документов, иерархии узлов, графа ссылок, очередей модерации и тикетов |
| Фоновые задачи и воркеры | Taskiq поверх Redis | Надежное исполнение очередей Copilot, асинхронного обогащения (re-embedding), кластеризации и аналитики |
| Кластеризация и темы | UMAP, HDBSCAN, c-TF-IDF | Батчевая группировка обращений для выявления аномалий и матрицы пробелов |
| Генеративная LLM (Продакшн) | Отечественные API: GigaChat-2 Max (резерв: YandexGPT 5 Pro) | Формирование ответов по контексту в строгом соответствии с 152-ФЗ с Structured Outputs |
| Роутер и классификатор | Отечественные API: GigaChat-2 Lite (резерв: YandexGPT 5 Lite) | Единый вызов: интент, тема, приоритет (P0/P1/P2), линия поддержки (L1/L2/L3), код ошибки |
| Буферизация предложений | razdel | Выделение границ русских фраз в потоке токенов без разрыва сокращений |
| Оценка и трассировка | RAGAS (LLM-Judge через GigaChat-2 Max) и Langfuse | Замер метрик на эталонном датасете и сквозное профилирование вызовов |

### Аппаратная конфигурация и жесткая фиксация моделей (16 ГБ VRAM)
Для исключения неопределенности и накладных расходов развертывания стек жестко фиксируется в следующей конфигурации:

1. **Локально на GPU (конфигурация 16 ГБ VRAM):**
   * Развертываются **строго два сервиса TEI**:
     * Контейнер TEI с `BAAI/bge-m3` (эмбеддинги dense) — потребление $\approx 1.5$ ГБ VRAM.
     * Контейнер TEI с `BAAI/bge-reranker-v2-m3` (Cross-Encoder реранкер) — потребление $\approx 1.5$ ГБ VRAM.
   * Суммарная утилизация GPU составляет $\le 3.5$ ГБ VRAM, оставляя запас видеопамяти под пиковые батчи.
   * **Локальный сервер vLLM для генерации не разворачивается.**
2. **Генеративная LLM и LLM-роутер (Внешние отечественные облачные API):**
   * Генерация ответов пользователям и черновиков Copilot: строго внешние отечественные API с нативной поддержкой Structured Outputs — `GigaChat-2 Max` (основной провайдер) и `YandexGPT 5 Pro` (резервный провайдер).
   * Маршрутизация и классификация (роутер): `GigaChat-2 Lite` (основной) и `YandexGPT 5 Lite` (резервный).
3. **Оценка RAGAS (LLM-Judge):**
   * Выполняется через то же внешнее отечественное API (`GigaChat-2 Max`).
4. **Требование к структурированному выводу:**
   * Провайдер модели обязан поддерживать структурированный вывод по переданной схеме JSON (JSON Schema / Pydantic).
   * При отсутствии нативной поддержки выполняется программная валидация схемы через Pydantic. При ошибке формата инициируется один повторный запрос. В случае повторного сбоя конвейер переключается на детерминированный аварийный сценарий из Раздела 3.3.
5. **Полное исключение зарубежных API:**
   * Зарубежные API строго исключены из всех контуров системы: контура исполнения (Runtime), контура обработки входящих документов (Ingestion) и контура оценки (Evaluation). Допускается их применение исключительно до старта хакатона для синтетической части проверочного датасета по открытым нормативным актам.

## 2. Конвейер обработки документов (Ingestion) и структура базы знаний

### 2.1. Сквозной порядок обработки файлов

```
[Методички и инструкции PDF/DOCX]     [Таблицы FAQ XLSX/CSV]     [Законодательство 44/223-ФЗ]
  (kb_type = 'guide')                   (kb_type = 'faq')           (kb_type = 'regulation')
         │                                      │                               │
         ▼                                      ▼                               ▼
[1. Docling: Разбор AST и таблиц]   [Прямой импорт пар FAQ]         [1. Docling: Разбор AST]
         │                          (Синтетические documents/nodes)             │
         ▼                                      │                               ▼
[2. Разделение представлений таблиц]            │                   [2. Выделение статей/частей]
   ├─► Индекс поиска: key-value факты           │                               │
   └─► Контекст LLM: сетка Markdown             │                               │
         │                                      │                               │
         ▼                                      │                               ▼
[3. Иерархический чанкинг по AST]               │                   [3. Чанкинг по статьям]
   └─► Чанки <= 350 токенов                     │                      (merge < 80 токенов)
         │                                      │                               │
         ▼                                      │                               ▼
[4. Мгновенная базовая запись в БД] ◄───────────┴───────────────────────────────┤
   ├─► PostgreSQL: documents ─► nodes ─► chunks (context_prefix = NULL)         │
   ├─► Qdrant (knowledge_base): первичный dense (сырой текст) + BM25            │
   └─► Поиск доступен пользователям сразу!                                      │
         │                                                                      │
         ▼                                                                      │
[5. Асинхронное фоновое обогащение (воркер Taskiq)] ◄───────────────────────────┘
   ├─► context_prefix: 1-2 предложения (GigaChat-2 Lite)
   ├─► hyp_questions: 3 вопроса поставщика (при ENABLE_HYPE = true)
   ├─► Re-embedding чанка с учетом context_prefix (TEI bge-m3)
   └─► Re-upsert обновленной точки в Qdrant (knowledge_base)
```

Построение графа ссылок `article_references` выполняется регулярными выражениями во время разбора текста по шаблонам «статьей N настоящего Федерального закона», «частью N настоящей статьи», «пунктом N.N настоящего Регламента». Неразрешенные ссылки сохраняются в поле `raw_label` со значением `to_node_id = NULL`.

### 2.2. Правила обработки таблиц, текста и обогащения
1. **Приоритет форматов источников:** При наличии версий документов в HTML или DOCX обработка выполняется напрямую из них. PDF-пайплайн задействуется только при отсутствии структурированных файлов. Таблицы XLSX и CSV загружаются напрямую в базу решений.
2. **Типизация источников (`kb_type`):**
   * `guide`: Официальные регламенты Портала поставщиков, руководства пользователя, пошаговые инструкции (основной корпус).
   * `regulation`: Федеральные законы (44-ФЗ, 223-ФЗ), постановления Правительства.
   * `faq`: Канонические пары «вопрос-ответ» (прямой импорт XLSX/CSV или утвержденные модератором решения).
   * `tech`: База знаний технических инцидентов (коды ошибок, плагины ЭЦП, КриптоПро).
3. **Прямой импорт готовых FAQ из XLSX/CSV (в обход Docling AST):**
   * Для каждой таблицы формируется синтетическая запись в `documents`:
     `doc_id = 'DOC_FAQ_' || md5(filename)`, `title = filename`, `regime = 'MOS_PORTAL'`, `status = 'ACTIVE'`, `edition_date = CURRENT_DATE`.
   * Формируется синтетический родительский узел в `nodes`:
     `node_id = 'NODE_FAQ_' || md5(filename)`, `doc_id = doc_id`, `level = 'item'`, `section_path = 'FAQ Import > ' || filename`, `title = 'База типовых вопросов'`, `full_content = '...'`, `token_count = 0`.
   * Каждая пара «вопрос-ответ» сохраняется в `chunks` с `node_id = 'NODE_FAQ_' || md5(filename)`, текстом `Вопрос: ...\nОтвет: ...`, `context_prefix = NULL` и индексируется в Qdrant с `kb_type = 'faq'`, `kind = 'qa_pair'`. Это гарантирует соблюдение внешнего ключа `chunks.node_id REFERENCES nodes(node_id)`.
4. **Два представления табличных данных:**
   * **Для поискового индекса:** Каждая строка таблицы преобразуется в плоский текстовый факт с привязкой колонок: `Сумма закупки: до 3 млн руб.; Размер обеспечения: 0.5%; Срок возврата: 5 рабочих дней`.
   * **Для контекста генерации:** Исходная табличная сетка сохраняется в чистом Markdown в поле `table_md` и передается языковой модели в оригинальном виде.
5. **Обработка объединенных ячеек:** Алгоритм Header Propagation разворачивает вертикальные объединения ячеек (`rowspan`), протягивая значение родительской категории во все дочерние строки.
6. **Контроль полноты парсинга:** После завершения работы Docling суммарный объем символов сверяется с текстовым слоем PyMuPDF. При расхождении более 5% файл отправляется на ручную проверку.
7. **Контекстуализация и фоновый Re-upsert (Contextual Retrieval + HyPE):**
   * При первичном парсинге чанк сохраняется с `context_prefix = NULL`. Он сразу доступен для гибридного поиска по `text`.
   * В фоновом режиме воркер `Taskiq` обращается к `GigaChat-2 Lite` для получения:
     * `context_prefix`: 1–2 предложения, поясняющие положение фрагмента в структуре документа.
     * `hyp_questions`: 3 гипотетических вопроса с формулировками поставщика (коротко, с отраслевыми аббревиатурами КС, НМЦК, СМП, без упоминания номеров статей).
   * После получения `context_prefix` воркер обновляет запись в PostgreSQL, пересчитывает плотный вектор `bge-m3` через TEI для строки `context_prefix + "\n" + text` и выполняет re-upsert вектора и payload в Qdrant.
   * Точки гипотетических вопросов сохраняются с признаком `kind = 'hypq'` и ссылкой на базовый `chunk_id`. Индексация гипотетических вопросов активируется флагом `ENABLE_HYPE = true` (по умолчанию `false`).
   * **Изоляция вспомогательного текста:** После дедупликации кандидатов (`group_by chunk_id` в Qdrant либо клиентской фильтрацией по первому вхождению `chunk_id`) в сервис реранкинга и в контекст языковой модели передается **исключительно текст базового чанка** (`context_prefix + "\n" + text`). Текст `hyp_questions` в реранкер и контекст LLM не передается.
8. **Инкрементальная индексация:** Команда консоли `ingest --doc <file>` изолированно выполняет разбор, чанкинг, обогащение и вставку одного документа без необходимости полной переиндексации базы.

### 2.3. Иерархическая схема хранилища PostgreSQL

```sql
-- Таблица документов, методичек и загруженных файлов
CREATE TABLE kb_documents (
    doc_id VARCHAR(64) PRIMARY KEY,
    title TEXT NOT NULL,
    regime VARCHAR(32) NULL DEFAULT 'MOS_PORTAL',
    edition_date DATE NULL DEFAULT CURRENT_DATE,
    status VARCHAR(16) NOT NULL DEFAULT 'uploaded',
    error_message TEXT NULL,
    source_url TEXT NULL,
    created_at TIMESTAMPTZ NOT NULL DEFAULT clock_timestamp(),
    updated_at TIMESTAMPTZ NOT NULL DEFAULT clock_timestamp(),
    CONSTRAINT chk_document_status CHECK (status IN ('uploaded', 'indexing', 'indexed', 'failed', 'deprecated'))
);

CREATE INDEX idx_kb_documents_status ON kb_documents (status);

-- Иерархические узлы структуры документов
CREATE TABLE kb_nodes (
    node_id VARCHAR(64) PRIMARY KEY,
    doc_id VARCHAR(64) NOT NULL REFERENCES kb_documents(doc_id) ON DELETE CASCADE,
    parent_node_id VARCHAR(64) REFERENCES kb_nodes(node_id) ON DELETE CASCADE,
    level VARCHAR(16) NOT NULL,          -- 'document', 'section', 'article', 'part', 'item'
    section_path TEXT NOT NULL,          -- 'Инструкция поставщика > Раздел 3 > Пункт 3.2'
    article_no VARCHAR(32),              -- NULL для методичек, '44', '96' для законов
    part_no VARCHAR(32),                 -- NULL для методичек, '1', '3' для законов
    title TEXT NOT NULL,
    full_content TEXT NOT NULL,
    table_md TEXT,                      -- Исходная Markdown-сетка таблиц при наличии
    token_count INTEGER NOT NULL,
    created_at TIMESTAMPTZ NOT NULL DEFAULT clock_timestamp()
);

CREATE INDEX idx_kb_nodes_lookup ON kb_nodes (doc_id, article_no, part_no);
CREATE INDEX idx_kb_nodes_path ON kb_nodes (doc_id, section_path);
CREATE INDEX idx_kb_nodes_parent ON kb_nodes (parent_node_id);

-- Поисковые чанки узлов
CREATE TABLE kb_chunks (
    chunk_id VARCHAR(64) PRIMARY KEY,
    node_id VARCHAR(64) NOT NULL REFERENCES kb_nodes(node_id) ON DELETE CASCADE,
    text TEXT NOT NULL,
    context_prefix TEXT NULL,           -- NULL при первичном разборе; заполняется асинхронно
    hyp_questions JSONB DEFAULT '[]'::jsonb,
    embedding_model_version VARCHAR(32) NOT NULL,
    created_at TIMESTAMPTZ NOT NULL DEFAULT clock_timestamp()
);

CREATE INDEX idx_kb_chunks_node ON kb_chunks (node_id);

-- Таблица нормативного графа межстатейных ссылок
CREATE TABLE kb_article_references (
    id SERIAL PRIMARY KEY,
    from_node_id VARCHAR(64) NOT NULL REFERENCES kb_nodes(node_id) ON DELETE CASCADE,
    to_node_id VARCHAR(64) REFERENCES kb_nodes(node_id) ON DELETE SET NULL,
    raw_label TEXT NOT NULL             -- 'п. 4 ч. 1 ст. 93', 'п. 2.4 Регламента'
);

CREATE INDEX idx_kb_refs_from ON kb_article_references (from_node_id);
CREATE INDEX idx_kb_refs_to ON kb_article_references (to_node_id);

-- Очередь модерации базы знаний (FAQ)
CREATE TABLE faq_moderation_queue (
    id UUID PRIMARY KEY,
    ticket_id UUID NOT NULL REFERENCES tickets(id) ON DELETE CASCADE,
    question TEXT NOT NULL,
    answer TEXT NOT NULL,
    kind VARCHAR(16) NOT NULL,          -- 'normative', 'procedural'
    valid_until DATE NULL,
    linked_regulation_chunk_id VARCHAR(64) REFERENCES kb_chunks(chunk_id) ON DELETE SET NULL,
    status VARCHAR(16) NOT NULL DEFAULT 'PENDING',-- 'PENDING', 'APPROVED', 'REJECTED'
    reviewer_id UUID REFERENCES users(id) ON DELETE SET NULL,
    created_at TIMESTAMPTZ NOT NULL DEFAULT clock_timestamp(),
    reviewed_at TIMESTAMPTZ NULL,
    CONSTRAINT chk_faq_kind CHECK (kind IN ('normative', 'procedural')),
    CONSTRAINT chk_faq_status CHECK (status IN ('PENDING', 'APPROVED', 'REJECTED'))
);

CREATE INDEX idx_faq_moderation_status ON faq_moderation_queue (status) WHERE status = 'PENDING';

-- Очередь кандидатов на регрессионное тестирование и Golden Set
CREATE TABLE regression_candidates (
    id SERIAL PRIMARY KEY,
    query TEXT NOT NULL,
    expected_node_id VARCHAR(64) NOT NULL REFERENCES kb_nodes(node_id) ON DELETE CASCADE,
    generated_answer TEXT NOT NULL,
    corrected_answer TEXT NOT NULL,
    error_tag VARCHAR(32) NOT NULL CONSTRAINT chk_regression_error_tag CHECK (
        error_tag IN ('hallucination', 'retrieval_miss', 'out_of_kb', 'outdated_norm', 'tone')
    ),
    status VARCHAR(16) NOT NULL DEFAULT 'PENDING' CONSTRAINT chk_regression_status CHECK (
        status IN ('PENDING', 'APPROVED', 'REJECTED')
    ),
    created_at TIMESTAMPTZ NOT NULL DEFAULT clock_timestamp()
);

CREATE INDEX idx_regression_candidates_node ON regression_candidates (expected_node_id);
```

## 3. Маршрутизация, пре-роутинг и детерминированная обработка

### 3.1. Детерминированный пре-роутер нормативных ссылок
Перед обращением к языковым моделям входящий запрос анализируется регулярными выражениями на наличие прямых ссылок на нормативные акты:
1. **Режим прямого извлечения нормы (Lookup-режим):**
   * *Условие:* Запрос краткий, содержит маркеры запроса текста («что написано», «текст», «содержание», «покажи», «процитируй») и не содержит предметных условий сверх ссылки на закон.
   * *Действие:* Прямой SQL-запрос к таблице `nodes` по полям `(doc_id, article_no, part_no)`. Время ответа сервера составляет $\le 50$ мс `[CALIBRATE]` в обход векторного поиска и реранкера.
2. **Режим принудительного кандидата (Forced Candidate):**
   * *Условие:* Запрос содержит смысловой вопрос с упоминанием нормы («какой порядок возврата обеспечения по части 6 статьи 44 44-ФЗ при отмене закупки?»).
   * *Действие:* Указанная статья извлекается из `nodes` и принудительно добавляется в пул кандидатов реранкинга и контекст, а запрос направляется по стандартному конвейеру поиска.
3. **Неоднозначность нормативного документа:** Если номер статьи присутствует одновременно в 44-ФЗ и 223-ФЗ, а закон в вопросе не уточнен, система немедленно возвращает пользователю уточняющий диалог выбора закона.

### 3.2. Спекулятивный поиск и многозапросное слияние
* Входные данные роутера: последние $N=6$ сообщений диалога (роли, тексты, предварительно очищенные от персональных данных), текущий запрос пользователя и текущий статус сессии.
* Векторизация `dense` и лексический prefetch по сырому тексту запроса стартуют параллельно с вызовом роутера.
* При классификации интента как `chitchat` или `out_of_domain` результаты спекулятивного поиска сбрасываются, возвращается шаблонный ответ.
* **Многозапросное слияние (Multi-query Prefetch):** Выполняется один вызов Qdrant Query API со списком prefetch-запросов (по одному на `standalone_query` и каждый подзапрос из `sub_queries` для веток `dense` и `sparse`) с объединением нативным алгоритмом RRF. Forced-кандидаты пре-роутера подмешиваются в пул после слияния. Клиентский RRF используется как резервный механизм при аппаратных ограничениях версии базы.

### 3.3. Pydantic-контракт классификатора запроса, правила приоритетов и матрица линий

#### Детерминированные правила назначения приоритетов (Priority Rules)
* **P0 (Критический, плановый первый ответ оператора < 60 с):**
  * Угрозы обращения в суд, прокуратуру или жалоб в ФАС.
  * Прямое несогласие со списанием денежных средств или блокировкой обеспечения.
  * Наличие $\ge 3$ сообщений подряд в верхнем регистре (КАПС-ЛОК) либо критический порог агрессивности тональности.
* **P1 (Срочный инцидент, плановый первый ответ оператора < 180 с):**
  * Наличие кодов технических ошибок программного обеспечения (`0x[0-9A-Fa-f]{8}`).
  * Прямые указания на дедлайн: истечение срока подачи оферты, подписание контракта или завершение котировочной сессии в течение ближайших 24 часов.
* **P2 (Стандартный, плановый первый ответ оператора < 600 с):**
  * Все остальные типовые консультационные обращения и вопросы по функционалу.

#### Детерминированная матрица маппинга тем на линии поддержки (`topic` $\to$ `support_line`)

| Линия поддержки | Закрепленные темы (`topic`) | Базовое описание и правила переопределения |
|---|---|---|
| **L2 (Техническая)** | `digital_signature_plugin`, `technical_errors`, `api_integration`, `browser_compatibility` | Ошибки плагина ЭЦП, сбои КриптоПро, интеграции API, ошибки браузеров. **Правило переопределения:** наличие распознанного кода ошибки (`error_codes`) автоматически повышает линию минимум до **L2** независимо от темы. |
| **L3 (Экспертная/Правовая)** | `payment_delays`, `account_blocking`, `complaints_fas`, `contract_disputes` | Финансовые разногласия, блокировки личного кабинета, споры по обеспечению, официальные жалобы в ФАС, досудебные претензии. |
| **L1 (Первая линия)** | `registration_portal`, `catalog_navigation`, `quote_sessions_rules`, `general_faq`, `contract_conclusion`, `closing_documents`, `tender_cancellation`, `bid_security`, `contract_security`, `delivery_acceptance`, `electronic_store`, `other` | Стандартные процедурные вопросы по регламентам Портала поставщиков, навигация, порядок регистрации и подачи заявок. |

Роутер использует данную таблицу как базовую детерминированную основу. Повышение линии роутером разрешено исключительно при наличии явных сущностей (наличие `error_codes` $\to$ L2; финансовый конфликт/угроза иска $\to$ L3).

При превышении таймаута роутера `[CALIBRATE, ориентир 1.5 с]` конвейер переходит на детерминированный фолбэк:
`{intent: 'qa', standalone_query: raw_query, sub_queries: [], priority: 'P2', support_line: 'L1', topic: 'general_faq', follow_up_type: 'none'}`.

### 3.4. Регламент распознавания нецензурной лексики (Profanity Policy)
В точном соответствии с формулировкой задания хакатона:
> *«Реализовать механизм распознавания нецензурной лексики для автоматического завершения таких обращений и информированием пользователя о нарушении правил общения».*

1. **Правила детекции:**
   * Проверка выполняется детерминированно до обращения к языковой модели с помощью специализированного словаря ненормативной лексики, лемматизатора `pymorphy3` и алгоритма нормализации обфускаций (замена латинских символов-омоглифов, удаление разделительных точек, дефисов и звездочек).
   * Проверке подлежит исключительно ненормативный мат. Оскорбления без мата, эмоциональные междометия («блин», «черт», «бляха») и метки тональности роутера основанием для блокировки сессии не являются.
2. **Действие системы:**
   * Соединение немедленно прерывается отправкой события `event: session_terminated` со структурой:
     `{"reason": "profanity", "message": "Ваше обращение завершено в связи с нарушением правил общения (использование нецензурной лексики). Пожалуйста, сформируйте новое обращение в корректной форме."}`.
   * Сессия переводится в статус `TERMINATED_ABUSE`. Дальнейшая генерация и отправка сообщений в рамках данной сессии блокируются.
   * Ограничение не накладывает запрета на создание новой сессии тем же пользователем (блокировка по IP или учетной записи не производится).
3. **Обработка в режиме оператора (`OPERATOR_ACTIVE`):**
   * При фиксации нецензурной лексики в адрес оператора правило срабатывает автоматически: оператор получает системное уведомление в интерфейсе АРМ, сессия прерывается, а тикет переводится в статус `CLOSED_ABUSE`.
4. **Контроль качества и дашборд:**
   * Каждый инцидент фиксируется в счетчике «Нарушения правил общения» аналитического дашборда.
   * Контрольный тестовый набор включает 30 фраз (15 фраз с матом, включая обфусцированные варианты, и 15 фраз без мата с провокационными словами). Точность и полнота отсечения определяются метриками Profanity Precision и Recall `[MEASURE]`.

## 4. Двухстадийный гибридный поиск, FAQ Fast-Path и калибровка уверенности

### 4.1. Гибридный поиск в Qdrant
1. Поиск выполняется по единой коллекции `knowledge_base` с фильтрами по умолчанию: `status = 'ACTIVE'` и `kb_type IN ('regulation', 'guide', 'faq', 'tech')`.
2. **Поведение фильтра статуса и обработка устаревших норм (Golden Set):**
   * По умолчанию в поисковый контекст включаются только актуальные версии материалов (`status = 'ACTIVE'`).
   * **Ловушка на устаревшие нормы в эталонном датасете:** Если совпадение найдено исключительно среди документов и чанков со статусом `status = 'DEPRECATED'`, языковая модель обязана выдать ответ по специальному шаблону:
     *«Данная норма/инструкция утратила силу (редакция от ДАТА). Актуальный порядок регламентируется документом [Название], согласно которому: ...»*.
3. Запрос выполняет параллельный prefetch по плотному и разреженному векторам с глубиной 50 кандидатов на канал.
4. **Мягкий буст по интенту:** При совпадении типа базы `kb_type` с предпочтением интента роутера надбавка начисляется **к итоговому скору реранкера** $S \in [0.0, 1.0]$:
   $$S' = \min(1.0, \; S + [\text{CALIBRATE, ориентир } 0.02])$$
   К исходным RRF-скорам первичного отбора надбавки не применяются.

### 4.2. Реранкинг, быстрый путь FAQ и принятие решений
1. 40 кандидатов передаются в сервис TEI с моделью `bge-reranker-v2-m3`. Скор релевантности $S$ и пороговые значения рассчитываются строго относительно **нормализованного запроса `standalone_query`** (на первом шаге диалога он совпадает с исходным текстом). Подзапросы `sub_queries` применяются только для расширения первичного пула кандидатов и в итоговом скоринге не участвуют.
2. **Быстрый путь для типовых вопросов (FAQ Fast-Path):**
   * Fast-Path применяется **СТРОГО при одновременном выполнении двух условий**:
     1. `kb_type == 'faq'`
     2. `kind == 'qa_pair'` (прямой импорт XLSX/CSV либо утвержденный модератором Data Flywheel)
     и итоговый скор реранкера удовлетворяет условию $S \ge \tau_{\text{faq}}$ `[CALIBRATE, ориентир 0.9]`.
   * При выполнении обоих условий система отдает канонический ответ напрямую пользователю с указанием источника без обращения к генеративной модели (TTFT $\le 100$ мс).
   * **Защита от сырых методичек:** При совпадении с чанком методички или инструкции (`kb_type == 'guide'`), даже если его скор превышает $S \ge 0.9$, Fast-Path **СТРОГО ЗАПРЕЩЕН**. Запрос направляется по штатному конвейеру RAG со сборкой контекста (Parent Expansion) и генерацией ответа языковой моделью со сносками.
3. **Приоритет источников информации:**
   * Процедурные вопросы портала, навигация, регламенты котировочных сессий и подача оферт закрываются приоритетно из источников `guide`, `faq`, `tech`.
   * Нормативно-правовые споры, вопросы законодательства и условий обеспечения — из источников `regulation`.
4. **Калиброванный порог $\tau$ [CALIBRATE]:** Единый порог релевантности $\tau$ рассчитывается на этапе калибровки по максимуму F1-меры на эталонном датасете.
5. **Зона гистерезиса $[\tau - \delta, \tau)$ [CALIBRATE]:**
   * При $S_{\text{top1}} \ge \tau$ ответ генерируется языковой моделью по контексту.
   * При $S_{\text{top1}} \in [\tau - \delta, \tau)$ генерация разрешается с обязательной директивой в системном промпте указать пользователю на возможное неполное соответствие найденных материалов.
   * При $S_{\text{top1}} < \tau - \delta$ срабатывает мягкая эскалация (Soft Deflection): вывод заголовков трех наиболее близких узлов базы знаний и кнопки перевода на оператора.
6. **Семантический кэш в Redis [STRETCH]:** Ключевание кэша осуществляется по плотному вектору `standalone_query`. Попадание фиксируется при косинусном сходстве $> [\text{CALIBRATE, ориентир } 0.95]$ и совпадении `regime_hint`.

## 5. Сборка контекста (Context Assembly)

1. **Расширение до родительских узлов (Parent Expansion):**
   * **Для методичек и инструкций (`kb_type == 'guide'`):** Так как у пользовательских инструкций отсутствует жесткий законодательный уровень `part`, действует правило:
     *Родительским узлом (`parent`) считается ближайший предок по AST-дереву с объемом `token_count <= 2500` токенов `[CALIBRATE]`.*
     Если непосредственный родительский раздел превышает лимит 2500 токенов — в контекст передается сам узел чанка без расширения.
   * **Для нормативных актов (`kb_type == 'regulation'`):** Извлекается ближайший предок в таблице `nodes` с уровнем `level = 'article'` (для законов 44/223-ФЗ). Если статья превышает 2500 токенов, подтягивается предок уровня части (`level = 'part'`) либо пункта.
   * Повторяющиеся узлы дедуплицируются по `node_id`. Суммарный объем контекста ограничивается бюджетом 6000–8000 токенов `[CALIBRATE]`.
2. **Расширение по графу ссылок (Reference Expansion):**
   * Для кандидата Top-1 извлекаются связанные узлы из `article_references`.
   * Глубина обхода графа составляет 1, добавляется не более 2 связанных статей суммарным объемом до 1500 токенов `[CALIBRATE]`. Приоритет отдается ссылкам, чьи узлы уже попали в пул реранкинга.
3. **Оформление таблиц:** Таблицы передаются модели исключительно в исходной Markdown-разметке из поля `table_md`.

## 6. Генерация ответа, сквозной бюджет задержек и верификация

### 6.1. Сквозной бюджет задержек (Latency Budget)

| Этап конвейера | Плановый норматив | Фактическое значение по Langfuse |
|---|---|---|
| Промежуточный статус конвейера (`event: status`) | $\le 50$ мс | [MEASURE] |
| Классификация и роутинг запроса | $\le 1500$ мс | [MEASURE] |
| Параллельный поиск и Cross-Encoder реранк | $\le 400$ мс | [MEASURE] |
| Отправка найденных источников (`event: sources`) | $\max(\text{роутер}, \text{поиск}) + \text{реранк}$ | [MEASURE] |
| Потоковая генерация предложений (`event: sentence`) | $\text{sources} + \text{TTFT LLM}$ | [MEASURE] |
| Завершение генерации потока (`event: done`) | Зависит от длины ответа | [MEASURE] |
| Асинхронный NLI-аудит (`event: verification`) [STRETCH] | $\le 2000$ мс после `done` | [MEASURE] |

Все фактические значения фиксируются перед защитой на основе профилирования трейсов в системе Langfuse.

### 6.2. Потоковый протокол Server-Sent Events и деградация
* Протокол поддерживает события: `status`, `sources`, `sentence` (с инлайн-флагом `verified: true/false`), `token` (опционально для посимвольной анимации), `done`, `escalate`, `verification` (NLI-аудит) и `degraded_mode`.
* При недоступности или тайм-ауте генеративной LLM сервер возвращает событие `event: sources` с найденными статьями базы знаний, заголовки Top-3 узлов, кнопку перевода на оператора и событие `event: degraded_mode` без передачи 500 ошибки клиенту.
* При низкой уверенности модели ($S_{\text{top1}} < \tau - \delta$) или запросе оператора конвейер отправляет событие `event: escalate` и ставит обращение в очередь операторов.

### 6.3. Двухуровневый контур верификации фактов
1. **Уровень 1: Инлайн-проверка слотов (время выполнения $\le 1$ мс на фразу):**
   * Регулярными выражениями во фразе со сноской выделяются числовые значения, проценты и номера статей (календарные даты исключены).
   * Числительные, записанные словами, нормализуются в цифры с обеих сторон.
   * Допустимое множество значений:
     $$\text{ValidValues} = \text{Числа контекста} \cup \text{Числа вопроса} \cup \{a \cdot b, \; a \cdot b / 100\}$$
   * **Обязательное условие сноски:** Предложение, содержащее число, процент или номер статьи и **не содержащее сноски** `[^N]`, автоматически получает статус `verified: false`.
   * При несовпадении слота фраза не подменяется, а отдается с параметром `verified: false` для подсветки в клиентском интерфейсе.
   * *Ограничение:* Уровень 1 выявляет галлюцинации чисел, но не определяет факты подмены контекста местами (задача уровня 2).
2. **Уровень 2: Асинхронный NLI-аудит [STRETCH]:**
   * После события `event: done` малая отечественная модель или локальный NLI-классификатор выполняет проверку логического следования утверждений из первоисточника, отправляя событие `event: verification`.

## 7. Контрольный оценочный контур и тестирование на реальных кейсах

### 7.1. Структура и изоляция эталонного датасета
1. В день выдачи данных организаторов контрольный датасет (200 пар) пересобирается:
   * **Практическая часть ($\ge 40\%$):** Формируется на основе реальных обращений поставщиков, предоставленных организаторами, либо официального FAQ Портала поставщиков и вопросов команды в роли поставщиков.
   * **Синтетическая часть (до 60%):** Генерируется строго отдельной моделью и по другому промпту, изолированно от контура ingestion.
2. В выборку включается 20% специальных проверок: вопросы по устаревшим нормам, запросы по нескольким разделам сразу, узкоотраслевые сокращения.

### 7.2. Целевые метрики качества

| Метрика конвейера | Назначение и формула | Норматив |
|---|---|---|
| Recall@40 первичного поиска | Доля релевантных узлов среди 40 кандидатов после слияния RRF до реранка | [MEASURE] |
| MRR (Mean Reciprocal Rank) | Обратный ранг целевого документа после Cross-Encoder реранкинга | [MEASURE] |
| Faithfulness (RAGAS) | Доля утверждений ответа, подтвержденных контекстом (LLM-Judge GigaChat-2 Max) | [MEASURE] |
| Factual Slot Precision | Доля корректно проверенных чисел и процентов без ложных тревог | [MEASURE] |
| False Deflection Rate | Доля необоснованных отказов в ответе на ответимые вопросы | [MEASURE] |
| Profanity Precision / Recall | Точность и полнота выявления нецензурной лексики на 30 тестовых фразах | [MEASURE] |

### 7.3. Конфигурация профилей эмбеддингов для A/B тестирования
Параметры векторного пространства выносятся в конфигурационный объект `embedding_profile`:
* `BAAI/bge-m3`: размерность 1024D, без префиксов (основной профиль);
* `deepvk/USER-bge-m3`: размерность 1024D, без префиксов;
* `ai-forever/FRIDA`: размерность 1536D, префиксы `search_query:` для запроса и `search_document:` для документов.
Коллекция создается под выбранный профиль, переключение модели в тестах A/B не требует модификации логики приложения.

### 7.4. Протокол проверки генерации гипотетических вопросов (HyPE)
Проводится параллельный прогон при `ENABLE_HYPE = false` и `ENABLE_HYPE = true`. Механизм признается успешным при приросте $\Delta\text{Recall@40} \ge +0.03$.

### 7.5. Поведенческое тестирование системы
Проводится проверка сценариев:
1. Корректность выдачи Soft Deflection на вопросах вне предметной области портала;
2. Мгновенное прекращение сессии при передаче нецензурной лексики;
3. Точность маршрутизации обращений по линиям поддержки L1, L2, L3;
4. Замыкание петли обучения при добавлении канонизированного FAQ.

## 8. АРМ оператора, линии поддержки и ассистент AI Copilot

### 8.1. Идентификация линий поддержки (Support Lines)
Вводится детерминированная классификация обращений по линиям поддержки (`support_line`):
* **Линия L1 (Первая линия):** Навигация по интерфейсу портала, типовые процедурные вопросы по методичкам, регистрация и базовые консультации.
* **Линия L2 (Вторая линия — Технические инциденты):** Ошибки плагина ЭЦП, сбои КриптоПро, аппаратные ошибки браузера, интеграции по API, сбои функционала подписания оферт. Наличие кодов ошибок в запросе автоматически повышает линию минимум до L2.
* **Линия L3 (Третья линия — Экспертная и правовая поддержка):** Финансовые споры по блокировке и списанию средств, конфликтные ситуации, официальные жалобы в ФАС, запросы к разработчикам портала или юристам.

Базовое назначение линии выполняется по статической таблице соответствия темы `topic` $\to$ `support_line` (Раздел 3.3). Роутер имеет право повысить линию с фиксацией обоснования (например, при обнаружении кодов ошибок).

### 8.2. Базовый сценарий обработки обращения и Handover
**Инвариант жизненного цикла обращения:** В соответствии с архитектурой бэкенда [BACKEND_ARCHITECTURE.md](./docs/BACKEND_ARCHITECTURE.md) обращение (`ticket`) создается сервером автоматически при первом сообщении пользователя в чат со статусом `bot_processing`. Пока обращение находится в этом статусе, диалог обслуживает вопросно-ответная система RAG.

1. `bot_processing`: Первичная обработка вопросно-ответной системой. Потоковая генерация ответа со ссылками на источники нормативной базы.
2. `queued`: Пользователь нажал кнопку эскалации («Позвать человека») либо модель зафиксировала неуверенность. Тикет переводится в статус `queued` (с сохранением линии `line_id` и приоритета P0, P1, P2) и помещается в очередь Redis соответствующей линии (`L1`, `L2`, `L3`). Очередь тикетов в базе данных выбирается с сортировкой `(priority ASC, created_at ASC)`, обеспечивая соблюдение нормативов SLA (P0 < 60с, P1 < 180с, P2 < 600с). Фоновый воркер `Taskiq` генерирует карточку Copilot.
3. `assigned`: Балансировщик закрепляет тикет за наименее загруженным оператором с резервированием рабочего слота.
4. `in_progress`: Оператор открывает тикет в веб-интерфейсе АРМ. Начинается двусторонний диалог с клиентом, бот блокируется от генерации ответов.
5. `resolved`: Обращение успешно завершается либо оператором в АРМ (признак решения человеком: `assigned_operator_id IS NOT NULL`), либо клиентом при решении вопроса ботом (признак решения ботом: `assigned_operator_id IS NULL`). При закрытии оператором рабочий слот немедленно освобождается, клиенту направляется форма оценки. Возврат диалога от оператора боту исключен (при новом вопросе клиента создается новое обращение).

```
Пользователь                 Шлюз бэкенда                    АРМ Оператора
     │                            │                               │
     │── Сообщение в чат ────────►│── Статус: bot_processing ────►│ (Генерация RAG-ответа)
     │    │                       │                               │
     │    ├── Клик "Вопрос решен"►│── Статус: resolved ───────────►│ (Завершено ботом, assigned_operator_id IS NULL, опрос 👍/👎)
     │    │                       │                               │
     │    └── "Позвать человека" ─►│── Статус: queued ────────────►│ (Очередь линии L1/L2/L3 по SLA P0/P1/P2)
     │                            │    │                          │
     │                            │    ├─► Воркер Taskiq: Copilot ──►│ (Подготовка подсказки)
     │                            │                               │
     │                            │── Статус: assigned ──────────►│ (Слот зарезервирован)
     │                            │◄── Статус: in_progress ───────│ (Оператор открыл тикет)
     │◄── Сообщение оператора ────│◄── Ответ оператора ───────────│
     │                            │                               │
     │◄── Форма оценки (1-5) ─────│◄── Статус: resolved ───────────│ (Оператор завершил диалог, assigned_operator_id IS NOT NULL)
```

### 8.3. Контракт данных карточки AI Copilot

```python
from pydantic import BaseModel
from typing import List, Optional, Literal

class EvidenceItem(BaseModel):
    source_collection: str              # 'knowledge_base'
    kb_type: Literal['regulation', 'guide', 'faq', 'tech']
    document_title: str
    section_path: str
    reranker_score: float
    snippet: str

class ResolvedTicketItem(BaseModel):
    ticket_id: str
    support_line: Literal['L1', 'L2', 'L3']
    user_query: str
    solution_text: str
    similarity_score: float

class CopilotSuggestionCard(BaseModel):
    ticket_id: str
    assigned_line: Literal['L1', 'L2', 'L3']
    suggested_line_code: Literal['L1', 'L2', 'L3']
    summary: str
    suggested_response: str
    recommended_chunk_ids: List[str] = []
    evidence: List[EvidenceItem]
    similar_resolved_tickets: List[ResolvedTicketItem] # 3 похожих закрытых кейса из resolved_tickets
    suggested_action: Optional[str] = None
    trace_url: str                      # Ссылка на трассировку сессии в Langfuse
```

База закрытых тикетов предварительно засевается 30–50 историческими решениями (включая сбои ЭЦП и ошибки КриптоПро). Из карточки оператору доступна кнопка быстрой переадресации тикета на другую линию поддержки (`L1` $\to$ `L2`/`L3`) с сохранением истории диалога.

### 8.4. Обратная связь и категоризация правок оператора
При ручной правке предложенного черновика оператор в один клик указывает категорию расхождения:
* `hallucination`: Сгенерирован недостоверный факт или параметр.
* `retrieval_miss`: Документ присутствует в базе, но не попал в контекст поиска.
* `out_of_kb`: Необходимая инструкция отсутствует в материалах портала.
* `outdated_norm`: Предложена устаревшая редакция регламента.
* `tone`: Необходимость корректировки стиля или вежливости.

### 8.5. Контроль нормативов обслуживания (SLA Compliance)
Время первого ответа оператора контролируется раздельно по классам:
* **P0 (Критический):** $< 60$ с `[MEASURE]` (угрозы ФАС/суда, списание обеспечения, $\ge 3$ капс-сообщений);
* **P1 (Срочный инцидент):** $< 180$ с `[MEASURE]` (коды технических ошибок 0x..., дедлайн оферты/сессии < 24 ч);
* **P2 (Стандартный):** $< 600$ с `[MEASURE]` (все остальные обращения).

## 9. Двухуровневая кластеризация обращений и дашборд руководителя

### 9.1. Базовый сценарий категоризации запросов
* **Слой 1: Фиксированная таксономия (Real-time):** Определение темы запроса роутером в момент поступления по закрытому списку из 20 тем согласно Разделу 3.3.
* **Слой 2: Батчевая кластеризация непредвиденных тем (Discovery):**
  1. Выполняется фоновым воркером каждые 10–15 минут по алгоритму BERTopic.
  2. Векторы обращений `bge-m3` сжимаются алгоритмом UMAP до 5–10 измерений.
  3. Алгоритм HDBSCAN группирует точки с параметром минимального размера кластера от 8 до 15.
  4. Ключевые слова кластеров рассчитываются по алгоритму c-TF-IDF. Присвоение названий выполняется малой отечественной моделью либо формируется из c-TF-IDF терминов.
  5. Точки шума привязываются к ближайшему центроиду при косинусном сходстве $> [\text{CALIBRATE, ориентир } 0.75]$ либо относятся в категорию «Прочие вопросы».

### 9.2. Детекция всплесков инцидентов и матрица пробелов
1. **Детектор всплесков инцидентов (Spike Detector):** Расчет скользящего счетчика обращений по кластерам и кодам ошибок. Оповещение формируется при превышении текущей частоты в 3 раза по сравнению с медианой предыдущих окон либо при $z\text{-score} > 3$ `[STRETCH]`.
2. **Матрица регламентных пробелов:** Ранжирование тем по произведению $\text{Объем} \times \text{Доля } (S < \tau) \times \text{Доля эскалаций}$. Верхние строки формируют перечень тем для передачи методистам на разработку инструкций.

## 10. Оценка качества работы поддержки и содержательное заключение о системных проблемах

### 10.1. Сбор обратной связи пользователей
1. После каждого ответа бота и после закрытия тикета оператором пользователю отображаются кнопки оценки: 👍 / 👎, поле ввода текстового комментария, а для диалогов с оператором — дополнительная шкала от 1 до 5 звезд.
2. Отзывы сохраняются в таблице `feedback` ([API_CONTRACT.md](./API_CONTRACT.md)). Текстовые комментарии проходят маскирование персональных данных и векторизуются моделью `bge-m3` для последующей кластеризации.

### 10.2. Методика оценивания результатов работы технических специалистов
Индивидуальный показатель качества работы оператора (Operator Quality Score, OQS) рассчитывается на основе объективных наблюдаемых событий без использования оценок LLM:

$$\text{OQS} = w_1 \cdot \text{CSAT}_{\text{norm}} + w_2 \cdot \text{SLA}_{\text{compliance}} + w_3 \cdot (1 - \text{reopen\_rate}) + w_4 \cdot \text{FCR} + w_5 \cdot (1 - \text{avg\_edit\_distance})$$

* **Фиксированная нормализация показателя удовлетворенности $\text{CSAT}_{\text{norm}}$:**
  $$\text{CSAT}_{\text{norm}} = \frac{\text{доля\_положительных\_оценок\_лайк} + (\text{средняя\_оценка\_звезд} / 5.0)}{2.0}$$
  где `доля_положительных_оценок_лайк` рассчитывается как $\frac{\text{кол-во } 👍}{\text{кол-во } 👍 + \text{кол-во } 👎} \in [0.0, 1.0]$, а `средняя_оценка_звезд` нормируется к отрезку $[0.0, 1.0]$ делением на 5.0. При отсутствии одного из типов оценок используется доступный компонент.
* **Весовые коэффициенты `[CALIBRATE]`:** По умолчанию $w_1 = 0.35$ (удовлетворенность), $w_2 = 0.25$ (соблюдение SLA), $w_3 = 0.20$ (отсутствие переоткрытий), $w_4 = 0.20$ (решение с первого контакта), $w_5 = 0.0$ (штраф за редактирование черновика Copilot отключен — правка черновика поощряется).
* **Метрика FCR (First Contact Resolution):** Доля тикетов, закрытых без повторного обращения пользователя по той же теме в течение 72 часов.
* **Сравнение с медианой:** Показатели рассчитываются за скользящие окна (день, неделя, месяц). В карточке специалиста метрики отображаются в сравнении с медианой команды соответствующей линии, исключая составление публичных рейтинговых списков во избежание манипуляций.

### 10.3. Метрики качества донесения информации до пользователей
1. **Прокси ясности ответа (Clarity Proxy):** Доля диалогов, в которых после ответа бота или оператора пользователь задает уточняющий вопрос («не понял», «поясните подробнее», повтор вопроса). Детектируется классификатором по полю `follow_up_type: Literal['clarification', 'repeat']`.
2. **Прокси решения вопроса (Resolution Proxy):** Получение положительной оценки 👍 либо отсутствие повторных обращений по теме в течение 72 часов.
3. **Индекс читаемости (Readability Index) [STRETCH]:** Оценка структурированности, отсутствия избыточного канцелярита и наличия пошаговых действий по выборке ответов экспертной моделью по шкале от 1 до 5 (применяется для сводных аналитических отчетов).

### 10.4. Формирование содержательного заключения о системных проблемах
Фоновая задача формирует периодический аналитический отчет (запуск по кнопке в дашборде либо по расписанию):
1. **Выборка данных:** Извлечение массива отрицательных отзывов пользователей, тикетов с тегами `retrieval_miss`, `out_of_kb`, `outdated_norm`, кластеров с высокой долей скоров $S < \tau$ и зафиксированных всплесков системных ошибок.
2. **Кластеризация комментариев:** Группировка текстовых жалоб алгоритмом UMAP + HDBSCAN с выделением топ-10 проблемных кластеров.
3. **Генерация заключения отечественной LLM:** Формирование структурированного отчета по строгой схеме JSON:
   ```json
   {
     "period": "2026-02-01 - 2026-02-28",
     "summary": "Краткий аналитический обзор ключевых сложностей пользователей...",
     "systemic_issues": [
       {
         "title": "Массовые сбои подписания при обновлении плагина ЭЦП",
         "evidence_count": 142,
         "affected_line": "L2",
         "suspected_cause": "ui_defect",
         "examples": ["Не видит сертификат после апдейта", "Ошибка 0x80090016"],
         "recommendation": "Опубликовать инструкцию по очистке кэша плагина в FAQ и передать баг разработчикам."
       }
     ],
     "positive_patterns": ["Высокая оценка скорости консультаций по аккредитации"],
     "metrics_delta": {"csat_change": "+0.04", "fcr_change": "+0.02"}
   }
   ```
4. **Хранение и визуализация:** Отчет сохраняется в таблицу `quality_reports`, выводится на экран руководителя с возможностью перехода в исходные тикеты и экспортируется в форматы PDF и Markdown.

## 11. Контур самообучения и модерации базы знаний (Data Flywheel)

### 11.1. Базовый сценарий добавления решения
1. Оператор завершает диалог и нажимает кнопку «Сохранить в базу решений».
2. Текст проходит обязательную санитизацию (удаление тегов, разметки, промпт-инъекций) и двухэтапную деперсонализацию.
3. Проводится векторный поиск по коллекции `knowledge_base` (`kb_type = 'faq'`) для выявления семантических дубликатов.
4. Проект статьи направляется в таблицу `faq_moderation_queue`.
5. Методист подтверждает карточку в интерфейсе модерации.
6. Запись индексируется в коллекцию `knowledge_base` (`kb_type = 'faq'`, `kind = 'qa_pair'`) и мгновенно становится доступной поисковому контуру и Fast-Path.

### 11.2. Санитизация и двухэтапная анонимизация персональных данных (152-ФЗ)
* **Санитизация пользовательского ввода:** Удаление системных инструкций, HTML-тегов, ограничение максимальной длины текста и изоляция контекста разделителями.
* **Этап 1: Детерминированная фильтрация регулярными выражениями.** Поиск и маскирование номеров телефонов, адресов электронной почты, номеров оферт, а также ИНН (10 и 12 цифр) и СНИЛС с программной валидацией контрольных сумм по государственным стандартам.
* **Этап 2: Контекстная фильтрация отечественной языковой моделью.** Поиск ФИО, названий контрагентов, паспортных данных и нестандартных адресов.

### 11.3. Контроль дубликатов и жизненный цикл записей
1. **Дедупликация через kNN:** При косинусном сходстве с существующей статьей $> [\text{CALIBRATE, ориентир } 0.88]$ (с учетом сжатых косинусов модели `bge-m3`, порог калибруется на 20 парах парафраз) система блокирует создание дубликата и предлагает объединить формулировки.
2. **Жизненный цикл статьи:** Поля записи включают `kind` (`normative` или `procedural`), `valid_until`, `last_verified_at`, `linked_regulation_chunk_id`. При обновлении официального документа с `kb_type = 'regulation'` связанные записи `faq` автоматически переводятся в статус обязательной ревизии.
3. **Приоритет источников:** Нормативные требования извлекаются строго из официальных документов (`kb_type = 'regulation'`), а регламенты и инструкции площадки — из `guide`, `faq` и `tech`.
4. **Сбор обучающих пар:** Каждое подтверждение оператором статьи формирует пару (запрос, целевой чанк) для последующего дообучения реранкера.

## 12. Масштабирование, архитектура очередей и API-контракт

### 12.1. Горизонтальное масштабирование сервиса
* **Stateless API:** Серверный слой на базе FastAPI не хранит состояние сессий в локальной памяти процессов. Все сессии и состояния диалогов сохраняются в PostgreSQL и кэшируются в Redis. Обеспечивается горизонтальное масштабирование за балансировщиком нагрузки Nginx/Traefik.
* **Совместимость с Server-Sent Events:** Потоковая передача токенов клиенту не требует механизма привязки сессий (Sticky Sessions), так как контекст для каждого запроса поднимается из централизованного кэша Redis.
* **Масштабирование воркеров Taskiq:** Фоновые обработчики очередей масштабируются независимо по изолированным пулам задач:
  * очередь `copilot_queue`: оперативная предгенерация подсказок оператора;
  * очередь `ingestion_queue`: пакетный разбор, векторизация и асинхронное обогащение (`context_prefix`);
  * очередь `analytics_queue`: фоновая кластеризация обращений, расчет суточных метрик и сборка аналитических заключений;
  * очередь `dispatch_queue`: реактивное и периодическое распределение обращений между свободными слотами операторов.
* **Масштабирование поисковых компонентов:** Сервисы TEI масштабируются горизонтально в виде реплик за балансировщиком нагрузки с включенным динамическим батчингом. Векторная база Qdrant на этапе хакатона разворачивается в одноузловой конфигурации; архитектура поддерживает шардирование коллекции и репликацию узлов без изменения схемы данных.
* **Партиционирование базы данных:** Для обеспечения стабильности при высоких нагрузках таблицы `messages` и `feedback` партиционируются по интервалу времени создания (по месяцам).
* **Целевые ориентиры нагрузки `[MEASURE]`:** Пропускная способность диалогового API (целевой норматив $\ge 50$ RPS), 95-й перцентиль времени отклика до первого токена, скорость пакетной индексации методичек.
* **Развертывание:** Базовая поставка для демонстрации оформлена в виде единого файла `docker-compose.yml`. Переход в промышленную эксплуатацию предусматривает развертывание в кластере Kubernetes с использованием Helm-чартов.

### 12.2. Прикладной API-контракт системы
Полная спецификация реляционных таблиц приложения (`chats`, `tickets`, `messages`, `users`, `operator_profiles`, `ticket_feedbacks`, `ticket_audits`, `faq_moderation_queue`), REST-эндпоинтов, структуры SSE-событий диалога и системной шины АРМ оператора зафиксирована в отдельном документе [API_SPECIFICATION.md](./API_SPECIFICATION.md).

## 13. Комплаенс и обработка персональных данных (152-ФЗ)

### 13.1. Требования к моделям и контурам
* **Продакшн-контур:** Обработка запросов пользователей, классификация, генерация ответов, верификация и составление аналитических заключений выполняются строго на базе отечественных облачных API (`GigaChat-2 Max`, `YandexGPT 5 Pro`; роутер: `GigaChat-2 Lite`, `YandexGPT 5 Lite`) с поддержкой Structured Outputs. Поисковые модели разворачиваются локально на GPU в сервисах TEI (`bge-m3`, `bge-reranker-v2-m3`). Зарубежные API строго исключены из всех контуров.
* **Отечественные API-провайдеры:** Договорной контур взаимодействия с провайдерами предусматривает строгое отключение сохранения переданных пользовательских данных для дообучения моделей на стороне поставщика сервиса.

### 13.2. Регламент защиты персональных данных
1. Все диалоговые логи, персональные обращения и метаданные хранятся в закрытом контуре базы данных PostgreSQL и векторного хранилища Qdrant.
2. Перед передачей текста в любые языковые модели выполняется двухэтапное маскирование персональных данных (детерминированная валидация ИНН, СНИЛС, телефонов, email по стандартам ГОСТ + контекстная фильтрация).

## 14. Объем реализации (Scope), артефакты сдачи и сценарий демонстрации

### 14.1. Базовый объем для демонстрации (Must-have, не режется)
1. RAG-ответ со сносками на первоисточники и инлайн-бейджами первого уровня верификации на контрольных вопросах.
2. Мгновенный ответ по типовому вопросу через FAQ Fast-Path (`kb_type == 'faq' && kind == 'qa_pair'`) без обращения к LLM.
3. Переход «Позвать человека» $\to$ создание тикета с линией (`L1`/`L2`/`L3`) и приоритетом (`P0`/`P1`/`P2`) $\to$ карточка Copilot $\to$ ответ оператора $\to$ сбор отзыва 👍/👎.
4. Утверждение статьи в очереди модерации $\to$ повторный ввод вопроса $\to$ автономный ответ бота по новой статье.
5. Аналитический дашборд на синтетике (3000 обращений) с фиксацией всплеска ошибок ЭЦП, распределением по линиям и матрицей пробелов.
6. Запуск генерации содержательного заключения о системных проблемах с получением готового структурированного отчета.
7. Таблица контрольных метрик качества на эталонном датасете (Golden Set).

### 14.2. План оптимизации при дефиците времени (Порядок сокращения Stretch)
При нехватке времени компоненты исключаются строго в следующей последовательности:
1. Асинхронный NLI-аудит второго уровня (`event: verification`).
2. Генерация гипотетических вопросов (HyPE).
3. Расширение контекста по графу межстатейных ссылок (Reference expansion).
4. Автоматическая оценка читаемости текстов (Readability LLM-judge).
5. Генерация наименований кластеров через LLM (сохраняются термины c-TF-IDF).
6. Расчет статистического показателя всплесков по $z$-score (сохраняется кратность к медиане).
7. Семантический кэш в Redis.
8. Интерактивный калькулятор FTE в интерфейсе дашборда.

### 14.3. Обязательные артефакты для сдачи проекта
1. **Схема реализации в нотации BPMN:** Сквозная процессная диаграмма (обращение пользователя $\to$ пре-роутер и детекция нецензурной лексики $\to$ классификация темы и линии $\to$ ветвление FAQ Fast-Path / RAG / Soft Deflection $\to$ эскалация в АРМ по клику $\to$ работа оператора с Copilot $\to$ сбор отзыва $\to$ модерация базы знаний $\to$ генерация аналитического заключения). Статусы и события в схеме BPMN строго согласованы со спецификацией.
2. **Экспорт структурированной базы знаний:** Полная выгрузка базы материалов в форматах JSON и дерева каталогов Markdown.
3. **Отчет по результатам тестирования:** Таблица метрик качества на реальных кейсах организаторов и контрольном датасете.
4. **Презентационная выжимка (8 слайдов):** Документ [JURY_PRESENTATION_DECK.md](./JURY_PRESENTATION_DECK.md).
5. **Прикладной контракт API:** Документ [API_CONTRACT.md](./API_CONTRACT.md).

### 14.4. Сценарий сквозного демонстрационного показа (6–7 минут)
Демонстрация последовательно подтверждает выполнение каждого пункта официального задания:
1. **Типовой вопрос (FAQ Fast-Path):** Пользователь задает типовой вопрос по срокам подписания оферты. Поскольку совпадение найдено в `kb_type = 'faq'` с `kind = 'qa_pair'` со скором $S \ge 0.9$, система мгновенно отдает канонический ответ из базы FAQ без вызова LLM.
2. **Сложный вопрос с RAG и сносками:** Запрос по условиям обеспечения заявки по 44-ФЗ. Система выполняет гибридный поиск, строит структурированный ответ со сносками, таблицей условий и активирует инлайн-бейджи верификации чисел.
3. **Вопрос вне базы знаний (Soft Deflection):** Пользователь задает вопрос, отсутствующий в методичках. Поисковый скор ниже порога $\tau - \delta$ — система честно сообщает об отсутствии информации и выводит кнопку «Позвать оператора».
4. **Попытка ввода нецензурной лексики:** Пользователь отправляет сообщение с обфусцированным ненормативным матом. Система моментально прерывает сессию с уведомлением о нарушении правил общения и регистрирует инцидент в счетчике дашборда.
5. **Технический инцидент и эскалация по клику на линию L2 (без авто-тикетов):** В новой сессии пользователь вводит сообщение об ошибке КриптоПро `0x80090016`. Так как в базе знаний нет готового решения, бот честно сообщает об отсутствии точной инструкции, выводит кнопку «Позвать оператора» и предлагает эскалацию. Пользователь нажимает кнопку эскалации $\to$ выполняется эскалация существующего тикета по клику пользователя (перевод из bot_processing в status = 'queued', line_id = 'L2', priority = 'P1') без автоматической эскалации (роутер определил тему `technical_errors` и код ошибки `0x80090016`, назначив линию L2 и приоритет P1) $\to$ тикет мгновенно отображается в АРМ оператора во вкладке второй линии L2 с готовой карточкой AI Copilot.
6. **Работа оператора с Copilot и сбор отзыва:** Оператор открывает тикет, видит краткую сводку проблемы, похожие закрытые кейсы из коллекции `resolved_tickets` и готовый черновик ответа. Оператор вносит уточнение, указывает тег «Отсутствовало в базе знаний», отправляет ответ и завершает тикет. Пользователь ставит оценку 👍 и оставляет текстовый комментарий.
7. **Модерация и замыкание петли:** Руководитель открывает очередь модерации FAQ, проверяет карточку с замаскированными данными и подтверждает добавление. При повторном вводе вопроса про ошибку `0x80090016` бот отвечает автономно по добавленной паре `qa_pair`.
8. **Аналитический дашборд и заключение о проблемах:** Руководитель открывает дашборд: отображается распределение обращений по линиям L1/L2/L3, показатель соблюдения SLA (P0/P1/P2), оценка качества специалистов OQS с нормализованным CSAT и кластеры отзывов. По нажатию кнопки «Сформировать заключение» система генерирует структурированный отчет о системных сбоях плагина ЭЦП с рекомендациями для методистов и разработчиков.

## 16. Чек-лист финализации и заморозки спецификации

- [x] **`kb_type` содержит 'guide'; Fast-Path защищен условием `kb_type == 'faq' && kind == 'qa_pair'`:** Тип `'guide'` присвоен регламентам и методичкам; совпадение с чанком методички со скором $S \ge 0.9$ исключает Fast-Path и направляет запрос в штатный RAG.
- [x] **Критерии P0, P1, P2 и статическая таблица `topic` $\to$ `support_line` явно описаны:** Критерии P0 (ФАС/суд, обеспечение, капс-лок), P1 (коды ошибок `0x...`, дедлайн < 24 ч) и P2 зафиксированы; роутер использует детерминированную таблицу маппинга.
- [x] **Шаг 5 демо переписан на эскалацию по клику пользователя, без авто-тикетов:** Устранен конфликт с §8.2 — бот честно сообщает об отсутствии инструкции при ошибке `0x80090016`, пользователь кликает «Позвать оператора», выполняется эскалация существующего тикета по клику пользователя (перевод из bot_processing в status = 'queued', line_id = 'L2', priority = 'P1') без автоматической эскалации.
- [x] **`chunks.context_prefix` сделан NULL; описан re-upsert; описаны синтетические `nodes` для XLSX:** Базовый поиск доступен сразу после Docling; асинхронный воркер генерирует префикс и выполняет re-embedding + re-upsert; прямой импорт FAQ из XLSX/CSV создает синтетические записи в `documents` и `nodes`.
- [x] **Parent Expansion адаптирован под методички через ограничение `token_count <= 2500`:** Предок методички берется по AST с лимитом $\le 2500$ токенов `[CALIBRATE]`, при превышении передается сам узел чанка без расширения.
- [x] **Формула $\text{CSAT}_{\text{norm}}$ зафиксирована:** $\text{CSAT}_{\text{norm}} = (\text{доля\_положительных\_оценок\_лайк} + (\text{средняя\_оценка\_звезд} / 5.0)) / 2.0$.
- [x] **Железо зафиксировано (16 ГБ VRAM + внешние облачные API РФ):** Локально на GPU работают только TEI `bge-m3` и TEI `bge-reranker-v2-m3` ($\le 3.5$ ГБ VRAM); генерация и роутер — через отечественные API (`GigaChat-2 Max`/`Lite`, `YandexGPT 5 Pro`/`Lite`) с Structured Outputs; RAGAS LLM-judge — через то же API. Зарубежные API исключены.
- [x] **Все ссылки на файлы переведены в относительный вид (`./`):** Устранены все абсолютные локальные ссылки, файлы связаны ссылками `./API_CONTRACT.md` и `./JURY_PRESENTATION_DECK.md`.
