# Воркфлоу разработки (Matt Pocock Skills)

Единый регламент совместной разработки команды с AI-агентами в Antigravity. Содержит два раздела:
- **Вариант 1. Базовый** — стандартный сквозной процесс разработки фич от идеи до слияния.
- **Вариант 2. Расширенный** — специализированные инженерные сценарии (отладка багов, ручные настройки, передача контекста, аудит архитектуры).

---

## 0. Инициализация и структура проекта (Единоразово на старте)

Настройка репозитория перед началом работы.
**Команда:** `/setup-matt-pocock-skills`
- Трекер: **Local Markdown** (`.scratch/`)
- Доменная документация: **multi-context** (`CONTEXT-MAP.md`)

Структура файлов при командной разработке (мультиконтекст):
```text
.
├── .scratch/
│   └── <feature>/issues/  # Задачи и спеки изолированы по веткам/фичам
├── docs/
│   └── adr/               # Архитектурные решения (NNNN-slug.md)
├── src/ (или app/)        # Доменные модули системы
│   ├── auth/
│   │   └── CONTEXT.md     # Локальный глоссарий подсистемы Auth
│   └── billing/
│       └── CONTEXT.md     # Локальный глоссарий подсистемы Billing
├── AGENTS.md              # Инструкции для Antigravity со ссылками на трекер
└── CONTEXT-MAP.md         # Карта контекстов: маппинг доменов на пути к их CONTEXT.md
```

# Вариант 1. Базовый воркфлоу (Разработка фич)

```text
/wayfinder (или /grill-with-docs) → /to-spec → /to-tickets → /implement → /code-review → merge (/resolving-merge-conflicts)
```

## 1. Планирование

Разработчик берет задачу и проясняет архитектуру до написания кода.

### Вариант А: Крупный функционал
Используется, если задача слишком велика для одного контекстного окна.
**Команда:** `/wayfinder`
- Формируется цель задачи и генерируется карта из открытых вопросов.
- Каждый вопрос решается в отдельной чистой сессии:
  - `/research` — автономный поиск информации в фоне.
  - `/prototype` — создание проверочного UI или кода, который затем отбрасывается.
  - `/grill-with-docs` — обсуждение архитектурных решений с командой.

### Вариант Б: Изолированная фича
Используется для задач, помещающихся в одно контекстное окно.
**Команда:** `/grill-with-docs`
- Проводится интерактивное интервью. Агент исследует код и задает вопросы до полного взаимопонимания.
- По ходу обсуждения агент автоматически пополняет локальный `CONTEXT.md` затрагиваемого модуля (маршрутизируя через `CONTEXT-MAP.md`) новыми терминами и при необходимости создает отдельный файл ADR в `docs/adr/`.

## 2. Фиксация решений и нарезка задач

Выполняется сразу после завершения планирования.
> **Важно:** Обе команды вызываются в том же самом окне без очистки контекста (`/clear`), чтобы агент не потерял договоренности.

1. **Команда:** `/to-spec` (или `/to-spec #<номер_карты>` для wayfinder)
   - Синтезирует результаты обсуждения в единую спецификацию и сохраняет её в `.scratch/<feature>/issues/`.
   - Согласовывает точки стыка (seams), на которых будут писаться тесты.
2. **Команда:** `/to-tickets`
   - Нарезает спецификацию на независимые вертикальные задачи (tracer-bullet tickets).
   - Указывает зависимости между задачами, формируя список доступных к реализации тикетов.

## 3. Реализация

Разработчик берет из `.scratch/<feature>/issues/` очередную задачу без открытых зависимостей.

**Команда:** `/implement @.scratch/<feature>/issues/<номер-имя-тикета>.md`
- Запускается в новой, чистой сессии (`/clear`) в ветке фичи.
- **Разработка через тесты (TDD):** Агент создает падающий тест на согласованном стыке, пишет минимальный код, проверяет типы и добивается прохождения теста. Моки используются только для внешних границ.
- **Результат:** Завершенный коммит с тестами в ветку фичи.

## 4. Ревью ветки (до слияния)

Перед тем как вливать изменения в `main`, ветка проверяется на соответствие стандартам и исходной спецификации.

**Команда:** `/code-review main`
- Запускается в чистой сессии (`/clear`), чтобы исключить предвзятость (confirmation bias).
- Проверяет diff ветки относительно `main` по двум независимым осям:
  - **Standards:** соответствие соглашениям проекта и чистота кода по Фаулеру.
  - **Spec:** полнота реализации требований из спецификации в `.scratch/<feature>/issues/`.
- Найденные замечания устраняются до слияния.

## 5. Слияние с основной веткой

Когда все задачи фичи реализованы и проверены через ревью, ветка вливается в `main`.

1. Разработчик подтягивает свежий `main` в свою ветку.
2. Если возникают конфликты слияния (в коде или в `CONTEXT.md`):
   **Команда:** `/resolving-merge-conflicts`
   - Агент анализирует намерения обеих веток по коммитам и тикетам, аккуратно объединяя изменения.
   - Прогоняет тесты и проверку типов до коммита.
   - Доводит слияние до чистого коммита без отмены операции (`--abort`).
3. Ветка мержится в `main`.

# Вариант 2. Полный инженерный воркфлоу (Full Engineering)

Сквозной процесс для эпиков, задач с высокой неопределенностью, багов и командной работы с интеграцией всех навыков Мэтта Покока.

```text
/ask-matt → /wizard → /wayfinder (/research / /prototype / /to-questionnaire) → /to-spec → /to-tickets → /implement (/diagnosing-bugs / /handoff) → /code-review → /resolving-merge-conflicts → /improve-codebase-architecture
```

## 1. Навигация и подготовка окружения

1. **Роутер (при любых сомнениях):**
   **Команда:** `/ask-matt`
   - Анализирует текущую ситуацию и указывает, какой навык или ветвление использовать дальше.
2. **Инфраструктура и секреты (ручные шаги):**
   **Команда:** `/wizard`
   - Если задаче нужны внешние токены, базы данных, OAuth или миграции — агент генерирует пошаговый Bash-скрипт с экранами прогресса и безопасной записью в `.env` и CI.

## 2. Глубокое планирование и снятие неопределенности

1. **Карта решений задачи:**
   **Команда:** `/wayfinder`
   - Декомпозирует крупную цель на карту открытых вопросов и решений (decision tickets).
2. **Разрешение вопросов по карте (ветвления в отдельных сессиях):**
   - **Не хватает фактов/документации:** `/research` — фоновый агент собирает данные по первоисточникам в Markdown-отчет.
   - **Нужно проверить идею кодом (spike):** `/prototype` — быстрый одноразовый код или замер производительности, который затем отбрасывается.
   - **Вопрос требует решения команды/лида:** `/to-questionnaire` — генерация структурированного асинхронного опросника.
   - **Архитектурный выбор:** `/grill-with-docs` — детальное интервью, пополнение локального `CONTEXT.md` модуля через `CONTEXT-MAP.md` и фиксация ADR в `docs/adr/`.

## 3. Фиксация спецификации и нарезка тикетов

Выполняется в том же окне контекста сразу после разрешения вопросов карты.
1. **Команда:** `/to-spec` (или `/to-spec #<номер_карты>`)
   - Синтезирует результаты всех исследований в единую спецификацию.
   - Проектирует глубокие интерфейсы модулей и согласовывает точки стыка (seams) для тестов.
2. **Команда:** `/to-tickets`
   - Нарезает спецификацию на независимые вертикальные тикеты с графом зависимостей (`blocked_by`).

## 4. Реализация, отладка и управление сессиями

1. **Реализация тикетов:**
   **Команда:** `/implement @.scratch/<feature>/issues/<номер-тикета>.md`
   - Запуск каждого тикета в чистой сессии (`/clear`) строго по TDD на согласованном стыке.
2. **Если обнаружен сложный баг или регрессия:**
   **Команда:** `/diagnosing-bugs`
   - Строгий 6-фазный цикл. **Барьер:** агент обязан сначала создать падающую команду (тест, curl, CLI) в Red. Без этого менять код запрещено.
   - Минимизация репро → 3–5 гипотез → точечное инструментирование `[DEBUG-xxxx]` → фикс с постоянным регрессионным тестом.
3. **Передача контекста и сброс сессии:**
   **Команда:** `/handoff`
   - Если сессия перегружена или задачу нужно передать другому агенту/коллеге — сжимает контекст в переносимый транзитный файл.
4. **Контроль взаимопонимания:**
   **Команда:** `/wait-what`
   - Если агент выдал мутный или запутанный ответ — сбрасывает тон и объясняет простыми словами на базе терминов `CONTEXT.md`.

## 5. Двухосевое ревью ветки

Перед слиянием фичи с `main`.
**Команда:** `/code-review main`
- Запускается в чистой сессии (`/clear`). Параллельные субагенты проверяют diff по двум независимым осям:
  - **Standards:** чистота кода, стандарты репозитория, запахи по Фаулеру.
  - **Spec:** полнота реализации требований из тикетов и спецификации.

## 6. Слияние с основной веткой

1. Разработчик подтягивает свежий `main` в ветку фичи.
2. При наличии конфликтов в коде или в `CONTEXT.md`:
   **Команда:** `/resolving-merge-conflicts`
   - Анализирует намерения обеих веток по тикетам и коммитам, аккуратно сводит код, прогоняет тесты и делает чистый коммит без `--abort`.
3. Ветка мержится в `main`.

## 7. Профилактика техдолга (Периодически)

Запускается раз в несколько дней или перед масштабным рефакторингом для предотвращения энтропии («комка грязи»).
**Команда:** `/improve-codebase-architecture`
- Сканирует активно меняющиеся модули кодовой базы.
- Прогоняет кандидатов через Deletion Test и генерирует автономный визуальный HTML-отчет.
- Проводит с разработчиком grilling по выбранному кандидату и фиксирует архитектурное решение (ADR) по углублению интерфейсов.
