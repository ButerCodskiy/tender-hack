# ADR 0002: Перенос модели обращения в домен чата

* **Статус:** Принято
* **Дата:** 2026-09-09
* **Домен:** `backend/src/chat/`, `backend/src/operators/`
* **Спецификации:** [docs/DATABASE_SPECIFICATION.md](../DATABASE_SPECIFICATION.md), [docs/BACKEND_ARCHITECTURE.md](../BACKEND_ARCHITECTURE.md), [docs/API_SPECIFICATION.md](../API_SPECIFICATION.md), [docs/QUEUES_SPECIFICATION.md](../QUEUES_SPECIFICATION.md)

---

## 1. Контекст

В исходной документации сущность обращения (`TicketModel`) и таблица `tickets` были отнесены к домену операторов (`backend/src/operators/`).

При детальном анализе сквозного сценария выявлено:
1. Сессия обслуживания начинается непосредственно в клиентском чате. При отправке первого сообщения создается обращение в первичном статусе обработки ботом `bot_processing`.
2. Каждое сообщение в таблице `messages` ссылается на `tickets.id` через внешний ключ `ticket_id`.
3. Подключение оператора является вторичным шагом эскалации, который наступает только при неудовлетворительном ответе бота или явном запросе клиента и управляется сменой статуса обращения на `queued`.

## 2. Проблема

Размещение `TicketModel` в модуле `src/operators` приводит к архитектурному перекосу: базовый модуль клиентского взаимодействия `src/chat` вынужден импортировать ключевую сущность сессии из домена операторов с самого первого запроса клиента, когда операторы в процессе еще не участвуют.

## 3. Решение

1. Перенести декларативную модель `TicketModel` в модуль чата: `backend/src/chat/models.py`.
2. Базовые методы создания и поиска активных сессий обращений разместить в `TicketRepository` внутри `backend/src/chat/repository.py`.
3. Модель линий поддержки `SupportLineModel` разместить в `backend/src/operators/models.py`, поскольку классификатор линий (L1, L2, L3) относится к структуре службы поддержки и маршрутизации операторов. Внешний ключ `line_id` в таблице `tickets` ссылается на `support_lines.id`.
4. В домене операторов импортировать `TicketModel` из `src.chat.models` исключительно для работы очередей распределения, балансировщика нагрузки и назначения сотрудников.

## 4. Последствия

1. Модуль чата становится полностью самодостаточным для клиентских диалогов и сессий бота.
2. Исключена неестественная зависимость клиентского контура от операторского домена.
3. Полностью сохраняется контракт схемы базы данных и целостность внешних ключей.
